## Result on the owner hypothesis

**The forward pass found no surviving control-panel machinery, and the backward pass found none either.** This is a supported null result on the hypothesis as stated — _a separately allocated runtime object created only to present a narrower or readonly TypeScript surface over an existing entity_. No such object exists in `packages/drag2/src` at `f375e6b1`.

What the traversal found instead is that the package already answers this question the way the hypothesis says it should, and does so **explicitly and recently**, with the decision on the record:

- Every narrowing of an existing entity in the tree is **type-level and allocates nothing**, and each says so at its declaration: `BehaviorLiftSession` over `VisualLiftSession` (`src/kernel/presentation.ts:331` — "The kernel passes the _same object_ under the narrower type, so it costs no allocation"); `LifetimeScope` over `Lifetime` (`src/kernel/lifetimes.ts:31`); `InsertionFrameView` over the behavior's frame (`src/sortable/slots.ts:67` — "no view is ever materialized"); `InsertionRuntimeView` over `PresentationView` (`src/sortable/slots.ts:91` against `src/sortable/runtime.ts:36`); `Draft<Part>` over `Frame<Part>` (`src/kernel/frames.ts:91`).
- The one place a boundary was bought with runtime members — `RectIndex`'s four read accessors (`src/sortable/rect-index.ts:175,179,183,187`) and the hand-written `ReadonlyFloat64Array` (`:71`) — is an owner-routed decision taken **against** a runtime boundary on exactly the ground the hypothesis names. `d170-entity-ownership-boundary-claude.md:72`: "**The boundary is compile-time, deliberately.** A runtime boundary — a `Proxy`, or a defensive copy per rebuild — would cost per-access or per-rebuild work to constrain files that the type checker already reads, against CONTRIBUTING §1.1 (no runtime nannying)". The accessors allocate nothing (they return the class's own `Float64Array`/array fields), and the interface is hand-written rather than mapped for a _gate_ reason, not an encapsulation one: a mapped `Readonly<E>`/`Pick<E, …>` erases method-ness and would disarm `@typescript-eslint/unbound-method`, the instrument D-170 step 0 armed to make the migration safe. Justification recorded, current, and live.
- The three objects that most resemble the shape are each a real translation or a real owner-composition, and each was routed and settled before this pass: the `BehaviorSpec` adapters (`src/free-drag/spec.ts:1069`, `src/sortable/spec.ts` tail) exist because `BehaviorSpec` is a nested-namespace protocol record a flat class instance cannot be — D-170's own words; `KernelHost` (`src/kernel/kernel.ts:2365`) is assembled from four owners and withholds capabilities by design, which D-170 examined and declined to convert; `SortableController` / `FreeDragController` are the published consumer API, not a projection of a wider entity.

The two findings below are what the forward pass _did_ turn up: not machinery, but **surviving justification for machinery whose premise was retracted**. They are reported because a justification that outlives its decision is the failure this lens exists to catch, and because D-137 makes the tense rule normative for `src/`.

## Findings

### der-1 — Tier C — `thenOf`'s "One caller" clause justifies itself by a readiness gate D-41 deleted

**Finding.** `src/kernel/kernel.ts:1439–1441` carries, in the present tense, "**One caller.** The readiness gate is a declaration and a host signal rather than a second consumer thenable with the same hazards, so nothing on that path reads `then` at all."

**Current behavior / contract.** There is no readiness gate. D-41 (active) states: "The authored commit is serial, and the readiness gate is deleted. … `controller.ready(request)`, `ResolutionOptions`, `KernelHost.presentationCommitted()`, `rt.pendingRequest`, `authoredReady`, the acknowledgement deadline and the readiness-specific retarget lifecycle are all removed." D-33, which introduced the acknowledgement protocol, is **inactive**: "Retracted by D-41 (Revision 2). The whole protocol is deleted, not amended." D-7 — the settlement-gate decision the clause's vocabulary comes from — is **inactive**, superseded by D-155: "There is no gate left to default open." A whole-tree grep for `ready(`, `readiness`, `presentationCommitted` finds no such member, host signal or declaration anywhere in `src/`.

**Why it is a problem.** The clause is the stated ground for a load-bearing invariant — that `then` is read exactly once, on one path — and it grounds it in a second path that does not exist. A maintainer verifying the invariant is sent to look for a gate, finds none, and cannot tell whether the invariant lost a caller or the comment lost its referent. It is also the class of prose D-137 (active) makes normative for `src/`: "a maintainer comment may argue for what _is_ and may not narrate what _was_". This one does not read as narration — it asserts a live mechanism — which is why it survived the D-137 sweep that cleared strikethroughs, dates and phase numbers.

**Evidence / reproduction.** `src/kernel/kernel.ts:1439`. Decision projection at `f375e6b1`: D-33 `inactive`, D-7 `inactive`, D-41 `active` with the deletion clause quoted above. `grep -rn "readiness\|ready(\|presentationCommitted" packages/drag2/src` returns only comment text, no declaration.

**Required property.** Every present-tense justification in `src/` names a mechanism that exists in the tree it sits in. Where the reason for a constraint is retired, the constraint either carries a reason that is still true or stands on its own statement.

**Removal class.** Comment only — no runtime semantics, lifecycle, public API or ownership. The `thenOf` mechanism itself is independently justified by the paragraph above the clause and is not in question.

### der-2 — Tier C — two release-path comments justify code shape by the absence of a protocol that never shipped

**Finding.** `src/sortable/spec.ts:1471` ("there is no publication below it to guard, because nothing here holds a pending request for the **readiness protocol** to acknowledge") and `src/sortable/spec.ts:1494–1496` ("There is no **acknowledgement protocol** to publish a request for — no `ready()` to check an object's identity against, and so no reason to publish last and inside this effect").

**Current behavior / contract.** Same evidence as der-1: D-33 inactive, retracted whole by D-41. Both comments are negative — they explain why the code does _not_ do something — but the something is a protocol no reader of this tree can see, so the explanation cannot be checked against anything.

**Why it is a problem.** These are weaker than der-1 (neither asserts a live mechanism), and each is doing real work at its site: the first scopes a terminal barrier to the write it covers, the second fixes an ordering. But the _reason offered_ is the deliberation D-137 excludes rather than the property: "stating the alternative's property rather than the deliberation". The barrier at `:1472` is justified by what `retire()` nulls, which is checkable; the appeal to a retracted protocol adds nothing a reader can verify and pins two live comments to a decision that no longer exists.

**Evidence / reproduction.** `src/sortable/spec.ts:1471`, `:1494`. Decision projection at `f375e6b1`. D-137 active, quoted above.

**Required property.** A comment's ground is a property of the present tree. Where a shape is justified by an absence, the absence is stated as a property the code has, not as a protocol the code declines to implement.

**Removal class.** Comment only. Neither barrier nor ordering is in question; both are separately and correctly grounded at their sites.
