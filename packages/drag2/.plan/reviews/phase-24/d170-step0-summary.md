## Verdict

**Step 0 has not armed the gate, and the reasons are tooling, not architecture.** Two independent configuration defects mean no runnable command in this repository lints `drag2` with `@typescript-eslint/unbound-method` on. Both are repairable without touching D-170's design, and both are routed to `implementer`.

**The pass's blocking architectural claim does not survive validation.** gate-4 concluded that `host.cancel` and `host.destroy` "cannot report even after the migration" and framed that as the finding that would outlive a gate repair. It was established by a probe that retained the current `Readonly<{ cancel(): void; … }>` façade around a class implementation. That probe proves a real and narrower thing — a `Readonly<…>` mapped alias erases method-ness from the rule — but it does not model the intended migration, in which `KernelHost` **is** the class and the read sites see its instance type. Re-probed against that shape, **all four load-bearing reads report.** The claim is rejected on that half and the surviving half is canonicalized separately.

**D-170 is therefore not sent back to the architect.** The decision's step-0 precondition is unmet for tooling reasons; the class migration stays blocked until the repaired gate passes independent review; and one genuinely open coverage question is routed to the architect as non-blocking.

### Rejected

**gate-4, second half — "`host.cancel` / `host.destroy` cannot report even after the migration" — is rejected on evidence.** The pass's probe held the declared type at the read site fixed as `Readonly<{ … }>` while varying only the implementation. That configuration answers "does a class implementation behind a retained structural façade report?" (no), which is not the migration D-170 orders. Under the intended shape — `KernelHost` itself the class, the read sites receiving its instance type — the rule reports at every one of the four sites. Measured in this consolidation, one probe file, four shapes, root cwd, `--no-inline-config`:

| shape at the read site                                                                     | detached read reported? |
| ------------------------------------------------------------------------------------------ | ----------------------- |
| `class KernelHostClass { cancel(){} destroy(){} }`, read as `host: KernelHostClass`        | **yes** (both members)  |
| the same class instance type, spread as `{ cancel: host.cancel, destroy: host.destroy }`   | **yes** (both members)  |
| `Readonly<{ cancel(): void; destroy(): Promise<void> }>` — the pass's probe                | no                      |
| `type RectIndexLike = { invalidate(): void; retire(): void }` — unwrapped alias            | **yes** (both members)  |
| `Readonly<{ invalidate(): void; retire(): void }>` — same members, wrapper only difference | no                      |

Rows three and five isolate the mechanism exactly: identical members, the `Readonly<…>` wrapper the only variable. So the pass established a true fact about `Readonly<…>` and attached to it a claim about the migration that the fact does not prove. The rejection is of the attachment, not the fact — the fact is carried forward as Q-17.

**Stated so it can be argued with:** if the migration were to retain the `Readonly<…>` façade as the published `KernelHost` type over a class implementation, gate-4's conclusion would be correct as written. It is rejected because the owner states the façade does not survive, not because the pass's measurement was wrong.

## Tier reasoning

All four Tier B findings sit under the vocabulary's second clause — no program behaviour changes, but _an instrument the repository relies on is unsound_, or a record misleads a reader of it. F-291 and F-292 make the instrument unsound in effect; F-293 and F-294 make the record's account of it false. None is Tier A: no correctly integrated consumer observes anything different at `cd9445e9` from before it. F-295 is Tier C — the gap is between the comment and the configuration, and nothing currently depends on the stronger reading.

F-291 and F-292 are **not merged.** They share a symptom and nothing else: different files, different mechanisms (effective-configuration resolution versus project selection), and repairing either leaves the other intact. They are separate remediation units.

## Routing

- **F-291, F-292 → `implementer`.** The two tooling defects, together the whole of "the gate is not armed". Repair is bounded to `eslint.config.ts`'s override ordering / oxlint-config resolution and the root `Justfile`'s project selector; neither touches D-170's design. **Any repair must be verified from both a root cwd and a package cwd** — see the methodological note below.
- **F-293, F-294 → `implementer`.** Record corrections to D-170's step-0 landing note in `00-index.md` and `plan.md`: the count (thirteen → ten, 11 + 1 + 1 → 8 + 1 + 1), and the stated reason for the `createRectIndex` silence. F-294's correction is _not_ cosmetic — the record currently tells a future reader that step 1 arms the instrument, and it does not.
- **F-295 → `implementer`,** folded into the same record correction: the configuration comment states the instrument's scope, so it should state `ignoreStatic`.
- **Q-17 → `architect`, non-blocking.** The rule reads the **declared type at the read site**, not the implementation, and a `Readonly<…>` mapped alias erases method-ness. The gate's coverage after each conversion therefore depends on the converted entity's _published alias_ becoming the class instance type — which the owner has stated for `KernelHost` and which this consolidation has confirmed reports. What is not settled is the residue: `LinearShift` is `Readonly<{ … }>` (`linear-shift.ts:88`), and `sortable/assemble.ts:77,81,88,98` pushes `axis.insertion.retire`, `axis.retire`, `landing.retire` and `displacement.retire` into `retireHooks`, each **called detached** at line 185 — precisely the defect class F-274 records, and silent to the gate today. Whether D-170's conversions bring those aliases with them, and whether the coverage that remains uncovered is acceptable for steps 1–6, is a decision about D-170's own scope. **This consolidation states the fact and does not settle it.** It is explicitly not a reason to reopen D-170 as a whole, and not a blocker on repairing the gate.
- **The `no-shadow` half of F-280 carries no routing here.** Out of this report by instruction, and out of this consolidation: the owner does not plan to reactivate the rule, and an explicit shadowing policy is separate work. F-280 stays open for it, unchanged.

## What passed, re-verified

**The ten suppressions are narrow and correctly justified.** All are `eslint-disable-next-line` naming the single rule; none is file-level or blanket; each covers one expression, and none sits on a factory-to-class member. Read to their call or restoration sites in this consolidation: `.scripts/ce-hmr.ts:105` is a `STATE_KEY in prototype.define` membership test that never invokes; `ce-hmr`'s `originalDefine` is invoked as `originalDefine.call(registry, …)`; `kernel.ts:1444`'s `then` is re-supplied at `then.call(value, …)`; `q7.browser.test.ts`'s `originals` array holds restore slots assigned straight back onto their own elements, its called copy separately bound. Under a root-cwd run all ten are matched one-to-one by a report.

**The delta is step 0 only.** No class is introduced anywhere; the only added occurrence of the word is inside the configuration comment.

**"oxlint implements none" is true.** The operative half of the same sentence — "deliberately absent from this list and _enforced_" — is false in effect, which is F-291.
