### 1. `slotConstants()` in `packaging.node.test.ts` — proportionate, not over-broad in a way that misfires today

The helper reads `packages/box-quad/src/index.ts` from disk and regex-matches `^const NAME = <integer>;$` at module scope, returning every matched name for use in a `declaresSlot` regex.

- **I/O and regex-over-source-text are not new machinery for this file.** The file already opens with a doc block stating its whole method is source-level assertion rather than build-output or import-graph inspection ("It reads source, not build output, so it needs no build step"), and already contains a `declarations()` helper that walks the filesystem and a `reachableFrom`-style import-graph trace elsewhere in the suite. Reading `box-quad`'s source with `readFile` + regex is the same idiom applied to a second file, not a new category of mechanism introduced for this fix.
- **The alternative the finding forecloses.** The forbidden names are box-quad's _private_, unexported slot constants (`BOX_A`…`BOX_HEIGHT`, `SPACE_A`… `SPACE_ANCESTOR_ZOOM`, confirmed via `grep -nE '^const [A-Z][A-Z0-9_]* = [0-9]+;' packages/box-quad/src/index.ts`). There is no importable/introspectable surface to assert against instead — the names exist only as source text — so reading the source is the only mechanism that can make the guard track a rename, which is exactly F-233's required property ("a rename in the package that owns them carries the guard with it").
- **The vacuity guard (`expect(forbidden.length).toBeGreaterThan(0)`) is not incidental ceremony — it is the direct fix for the failure mode F-233 itself demonstrated**: a match target that stops matching (the literal `BOX_ANCESTOR_` after BQ-9's rename) makes the surrounding guard pass while testing nothing. Asserting the extraction itself is non-empty converts that exact failure mode from a silent green into a red. This is the kind of instrument-liveness check `.agents/docs/documentation.md` §7's witness table is concerned with, applied locally rather than left implicit.
- **"Over-broad by construction" is disclosed and, on the current tree, produces no false positive.** The regex also matches `BOX_LENGTH`, `SPACE_LENGTH` and `QUAD_LENGTH` — length constants, not slot indices — which the doc comment explicitly acknowledges ("any module-level `const NAME = <integer>` there qualifies... That is the safe direction"). I checked whether this widening currently produces a false positive: `grep -rnE '\b(BOX_LENGTH|BOX_A|BOX_B|BOX_C|BOX_D|BOX_E|BOX_F|BOX_WIDTH|BOX_HEIGHT|SPACE_LENGTH|SPACE_A|SPACE_B|SPACE_C|SPACE_D|SPACE_ANCESTOR_ZOOM|QUAD_LENGTH)\b' packages/drag2/src/free-drag packages/drag2/src/sortable` returns no matches — none of the fourteen forbidden names collides with anything in the two guarded directories today. The comment's own framing (the names are "box-quad's private vocabulary either way, and a behavior has no business restating one") is the argument that a same-spelled identifier in a behavior module is suspect regardless of whether it happens to be a length constant or a slot index, so the widening is a stated design choice with a stated justification, not an unexamined side effect. I looked for, and did not find, a case where that widening currently produces a false alarm.

**Verdict: clean.** The mechanism is exactly as large as the fix requires — one `readFile`, one regex extracting the vocabulary, one regex testing for it, one liveness assertion protecting the second regex from the exact silent-pass mode the finding reported.

### 2. `describe('the two published spaces', ...)` in `presentation.browser.test.ts` — helpers pull their weight, no duplication of the existing `lift()` helper

- **`acquire()` is not a rename of the file's existing `lift()` helper (line 75).** `lift(visual, mode)` always calls `acquireLift(visual, visual, mode, ...)` — item and visual are always the same reference — and returns only `.session`. F-234's test needs `item` and `visual` supplied as _different_ elements and needs the full acquisition object back (to read `.visualSpace`/`.itemSpace`, which `lift` discards). Neither capability exists on `lift()`, so `acquire()` is not duplicated machinery; it is the minimal helper that actually exposes what these two tests assert on. `mode` is fixed to `LIFT_IN_PLACE` rather than parameterized, correctly — nothing in the two tests varies it, and adding a parameter no call site uses would be exactly the over-parameterization the task asks about, which this helper avoids.
- **Two call sites for `acquire()`, two for `stage()`.** Per `CONTRIBUTING.md` §2.1, a single-use function is an inline candidate; these are not single-use. Both helpers remove real duplication: `acquire()` collapses a six-argument `acquireLift(...)` call plus a `sessions.push` line that would otherwise be repeated verbatim in both tests (the same six-argument shape appears at three other call sites in this file, at lines 76-86, 378-386 and 398-405, so the pattern of wrapping it locally is the file's established idiom, not a new one); `stage()` collapses a five-property `createBox` style object that both tests need transformed to keep either space from collapsing to the `null`-ancestry identity (documented in its own one-line comment).
- **Naming.** `acquire`/`stage` are scoped inside the `describe` block, so they do not collide with or shadow the file-level `lift`/`createBox` they wrap, and each carries a one-line comment stating what it is for, consistent with the rest of the file's helper style (e.g. the file-level `lift()` and `createBox()` doc comments).

**Verdict: clean.** Confirmed no duplicate helper already existed for the item/visual-diverging, full-acquisition-returning shape these tests need (`grep -n "function acquireLift\|acquireLift(\|createRealm(\|sessions\.push"` over the file, reviewed above), and confirmed the two-call-site threshold is met before either helper was introduced.
