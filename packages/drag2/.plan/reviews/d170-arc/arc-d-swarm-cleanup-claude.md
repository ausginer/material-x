## Findings

### cleanup-1 — tier C — the newly-authored `InsertionFrameView.snapshot` JSDoc, on a published third-party-facing type, carries maintainer rationale beyond a precondition

**Current behavior/contract.** `src/sortable/slots.ts`'s `InsertionFrameView` and `InsertionRuntimeView` are re-exported from `src/sortable/feature.ts` (confirmed: both names appear in its `export type { ... }` block), which is the published surface a third-party axis author (`AxisInstaller`) writes against. F-326 moves `snapshot` from `InsertionRuntimeView` onto `InsertionFrameView` in this range and gives it a new doc comment:

```ts
/**
 * **The collection the gap indexes into**, or `null` before a lift.
 *
 * It is the frame's own committed snapshot, which is what a rule needs it to
 * be: the release resolve runs after the frame has frozen, and a gap
 * resolved against a collection the frame has already stopped agreeing with
 * would name a slot in a list nothing else is reading. The behavior
 * recomputes the home gap from the same committed value for the same reason.
 */
snapshot: CollectionSnapshot | null;
```

**Why it is a problem.** `documentation.md` §5.1: a JSDoc block reaching a published `.d.ts` "contains only what a reader outside this repository can act on" and carries "**No rejected alternatives, and no defence of the design.** A consumer cannot act on why the other shape lost." `CONTRIBUTING.md`'s Comments-and-JSDoc section states the same rule. The actionable content here is one sentence — this is the committed snapshot, null before a lift. The second sentence is not a precondition the caller must meet; it explains an internal timing fact about `prepareRelease`/the release resolve running "after the frame has frozen" and defends why the field lives on the frame view rather than elsewhere — reasoning a third-party axis author writing `resolve`/`moved` has no way to act on and does not need in order to use the field correctly. `arc-d.md` and `plan.md` both record, as a measured cost, that this docblock is what moved the published-declarations figure from 116.39 kB to 116.43 kB raw — i.e. the extra prose is install weight the record itself prices, distinct from whether the prose belongs in a published block at all.

This is not an isolated style choice invented by this diff: the sibling `item` field on the same type (unchanged by this range) carries an equivalent paragraph ("It is read off the frame rather than off `InsertionRuntimeView`: … duplicating it onto the per-operation view would create a second copy that could drift"), and `box`'s docblock does too ("Nullable rather than normalized to identity, because …"). The convention is pervasive and pre-existing in this file, so this finding is about the newly-authored instance in scope, not a claim that the convention is novel to Arc D.

**Evidence.** `packages/drag2/src/sortable/slots.ts` (current tree, the `snapshot` field of `InsertionFrameView`); `packages/drag2/src/sortable/feature.ts` lines re-exporting `InsertionFrameView`/`InsertionRuntimeView`; `packages/drag2/.plan/measurements/arc-d.md` §"The one cost that went the other way is install weight" (116.39 kB → 116.43 kB, docblock cited by name); `packages/drag2/.plan/plan.md`'s 2026-09-09 entry ("Published declarations went the other way by about 40 B raw, which is `snapshot`'s docblock arriving on a published type").

**Required property.** Published JSDoc states only what an external reader can act on; internal design rationale — including a comparative "why this field lives here rather than there" — belongs in an internal comment or the record, not in the shipped block. This is a documentation-discipline finding, not a runtime-machinery one, and it is systemic to the file rather than unique to this range's addition — reported per instruction to name the violated property rather than to prescribe which of the several instances gets rewritten.

## Null results, stated explicitly

- **The `SortableActivation` record's membership (the core of the arc).** `#operation.activation` is built whole in one statement group (`spec.ts`, activation effect) and dropped whole in one statement group (`retire()`), with no code between either group — confirmed by reading both sites directly. All six members (`placeholder`, `lift`, `box`, `live`, `settle`, `space`) are `readonly`. No partial-record state is representable, matching the record's own stated invariant. This is a legitimate consolidation of duplicate/scattered per-operation state (`presentation`, `activePlaceholder`, `lift` as three separate fields carrying one lifetime) into one owning boundary — exactly what `CONTRIBUTING.md` §5 ("do not store what can be derived cheaply" / avoid multiple representations of one fact) and §9 (copies need an ownership reason) ask for, not machinery added beyond the code's responsibility. No finding.
- **`box`/`live`/`settle` copied onto the per-operation record despite controller lifetime.** These three are controller-lifetime values (`this.#slots.box`, `this.#live`, `this.#slots.settle`) duplicated per operation rather than read once. This is a real boundary with a stated ownership reason (a published view's structural requirement), not an unjustified copy — no finding.
