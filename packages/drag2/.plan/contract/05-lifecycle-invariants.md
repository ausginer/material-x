# 5. Lifecycle invariants, findings and open questions

The invariant table, open questions, measurements owed and test matrix are normative. Finding sections preserve the review history and rationale; where an older finding narrative conflicts with a later decision or documents 00–04, the later decision and documents 00–04 win.

## Invariants, by enforcement tier

I-1…I-28 are inherited from the shipped package and probe 1. **I-29 and I-30** were introduced by this model's failure and post-commit ordering rules, **I-31** by the Phase 8a amendment, **I-32…I-35 by the Phase 14 revision** (D-32, D-33, D-35), and **I-36 by Checkpoint D review 2** (C2-01), whose third review re-tiered **I-6** to carry in its own row the split I-36 had stated only in its mechanism cell (C3-03). **Revision 2 (D-36…D-47) touches four rows and adds one**: **I-35 is deleted** with the protocol it described (D-41), **I-6** is rewritten for deferred physical teardown (D-36), **I-36**'s domain is replaced by a finite API-shaped one (D-37), **I-31** is qualified for a destroyed controller (D-40), and **I-37** is new (D-38). The column that matters is the tier:

- **A — frame publication safety.** The violation does not compile, or is unexpressible through the API.
- **B — kernel-enforced sequencing.** The kernel orders it; a participant has no opportunity to get it wrong. Not a type property.
- **C — discipline.** A contract rule a participant must obey. The API permits violation.

Probe 1 had every one of these at tier C.

**A combined rating is not hedging.** Where a property is partitioned, the Tier column names both halves, because one letter over a compound statement overstates one half and hides the other. Three distinct relations wear the same label family and should not be read as one: a **precondition**, where the B guarantee holds mechanically and its meaning rests on a rule a participant obeys (I-34); a **sub-property** split, where a compound claim's named parts have different owners (I-5, I-12, I-35); and a **quantifier partition**, where one property is enforced by different parties over different call sites (I-6/I-36, I-32, and I-13, which carries its partition in the invariant's wording instead). An unqualified letter over a partitioned property is a defect, not a simplification — C3-03 is the last one found. **A tier-C half needs a stated limit as well as a stated owner.** C3-03 gave I-6's residue an owner and left its extent universal, and one pass later that produced a fourth residue against a clause no implementation could be shown to discharge. Where the C half is a residue rather than a disclaimer, state what it guarantees everywhere (a floor) and where it guarantees more (a register), so that a missing barrier can be classified instead of only counted — I-36 (2) and (3). **The instrument survives Revision 2; the contents of this register do not, and the difference is worth stating precisely.** Floor-plus-register was the right shape for a residue whose extent had to be bounded, and it remains the right shape for the next one. What D-37 withdraws is not the instrument but the entries: both ceilings — §[03](03-feature-composition.md) §`y()`/`xy()`'s "reads no further geometry" for the candidate loop, and the README's publication of it — are **withdrawn**, and the bracket section is subsumed, because under D-36's transaction bracket every consumer-reaching stretch that is not a declared-slot invocation is bracket-discharged by construction rather than by a written entry. **The sortable's register is therefore empty, and an empty register is not an unwritten one**: every site now gets D-37's finite domain and nothing more, and there is no longer any site at which this library promises more than it. A behavior that wants to promise more opens a register of its own; it does not inherit this one. **And the limit belongs in the invariant cell, not only in the mechanism cell.** Review 4 stated I-6's participant bound in the mechanism column while recording the headline beside it as retained verbatim, and one pass later a public conformance test required exactly what the headline forbade (C5-03). Both columns are normative; when they disagree a reader acts on the claim, not on the note about the claim. **Mechanism prose that reinterprets an invariant does not change the invariant's operative sentence** — if a decision bounds a guarantee, the bounded form is what the Invariant column must say.

## Findings

### F-1 — callback count · note, not a finding

Thirteen top-level `BehaviorSpec` members plus one optional, ~18 functions once the transitions expand, against probe 1's fifteen. A wash. The split is what buys tier A and B for I-2, I-3, I-5, I-16 and I-18, and grouping into `Transition` objects keeps the surface legible. `moved` stays a top-level field, so the hot path takes no extra property hop.

The Phase 14 revision moved this by one optional member (`command`, D-32) and ratified two that the implementation already had (`config.actionTags`, `reportFailure`). A whole second _input mode_ costing one optional member is the number worth reading here.

### F-2 — part factory determinism · open, tier C

`Object.assign`-based composition means the two frames of one controller share a map only if every part factory returns the same key set in the same order every time, and the kernel folds them in the same order. TypeScript proves neither.

Much narrower than before D-15, which removed the kernel-slice half of this finding entirely: the behavior can no longer mis-initialise fields it cannot name. **Mitigation:** the kernel folds from one code path, called twice, plus the `__DEV__` key-set assertion.

### F-4 — a closure graph per controller · accepted, measured

D-4 keeps the behavior's runtime private by capturing it in closures, so each controller allocates its own `BehaviorSpec` plus ~16 function objects, and each call site sees a different function identity.

The alternative — the kernel storing one opaque `S` and threading it as argument zero, making `BehaviorSpec` a module-level frozen constant — is better for memory and inline caches. The earlier rejection ("it requires the kernel to _hold_ behavior state, changing the honest description of H-2") **does not survive scrutiny**: holding an untyped reference does not make the kernel know, expose or structurally widen that value, and H-2's substance — that the kernel cannot reach into behavior state — is preserved exactly by a phantom `S`.

The closure model was said to ship "because it is simpler to specify, not because it is faster", with the measurement owed before that was treated as settled. **M-2 (2026-08-02 — [measurements/m2.md](../measurements/m2.md)) settles it, and inverts the second half of that sentence.**

- **Heap: the closure model costs 3.6×** — 506 B per controller against 141 B, stable from 100 to 1000 controllers. At 1000 controllers that is 356 kB.
- **Move call: the closure model is at least 2.9× faster** — 0.0013 µs against 0.0038 µs, because a captured closure is a direct call while the opaque-`S` form is a property load plus an indirect call with an extra argument.

The "better for memory and inline caches" expectation above was half right: it is better for memory, and worse on the path that runs every frame. Since performance is this repository's first code-style priority and the heap difference is under 20 kB at realistic controller counts, **the closure model is kept on the merits**, not on simplicity. The swap remains mechanical if a page ever holds enough controllers for 365 B each to matter.

### F-5 — `admit` runs inside native dispatch · resolved

Admission is the one kind of seam the kernel calls outside the queue, because `composedPath()`, handle resolution and the `preventDefault()` decision are meaningful only during native dispatch. A behavior can therefore throw into the browser's event loop rather than into the failure model. The wrap is three lines:

**Since D-32 this covers two members**, `admit` and `command.admit`, with identical treatment; and since C-03 the `preventDefault()` _call_ is the kernel's, made after the member returns non-null, so a member that throws never consumed the event.

**Revision 2 changes the policy, not the ownership** (D-46, specified normatively in §[02](02-kernel-behavior-contract.md)). The call stays the kernel's and is still made only on a non-null return — what changes is that admission must **decline** where it previously admitted and prevented. Probe E found eight of ten input cases release-blocking and **six of them never activated a drag at all**, so the damage is done by the admission `preventDefault()` alone, before any threshold is crossed: a press that never becomes a drag consumed focus, caret, selection and form-control behavior. The sharpest case is on the other ingress — a single `ArrowRight` inside a nested text input leaves the caret frozen and `defaultPrevented`, and produces a complete accepted reorder `{from:2,to:3}` from one keystroke, because command admission never asked what the event landed on. Default admission therefore declines on interactive and editable descendants, keyboard admission asks what the event landed on, and `event.isComposing === true` never admits. Nothing here re-opens C-03: only `pointerdown` was ever prevented, so click, `href` and ctrl-click were never at risk, and the decline path that carries the new policy is I-32's, which probe E confirms leaves native behavior wholly intact.

```ts
let visual: HTMLElement | null;
try {
  visual = spec.admit(event, draft);
} catch (error) {
  fail(FAILURE_ADMISSION, error); // queued, not thrown at the browser
  return; // draft abandoned; controller stays idle
}
```

Whether to adopt it is Q-1: the shipped package deliberately lets a throwing admission factory escape the listener, and the change is observable.

### F-7 — landing-target arithmetic duplicates across behaviors · accepted, minor

The behavior owns `anchorTarget`, because it is the party that knows where its footprint is. A second behavior reimplements the delta arithmetic. The answer is a **pure exported helper**, never a seam — probe 1's warning about the kernel becoming "a directory of unrelated helper functions" is about the seam surface, the thing a behavior author must implement.

### F-9 — the kernel cannot type the consumer resolution · neutral

`ResolutionCommand.invoke` threads an `unknown` back to `settlement.prepare` with a status code. Probe 1 already required the _behavior_ to validate that a fulfilled value is an explicit resolution; the kernel merely stops pretending to know a type it never inspected.

### F-10 — contribution objects are polymorphic at the assembler · non-issue

Each feature returns a differently-shaped literal, so the assembler's ~10 property reads are megamorphic. Construction time, once per feature. Recorded so it is not rediscovered as a hot-path concern.

### F-11 — reset exhaustiveness is unprovable · open, tier C, inherited

Nothing proves `resetFramePart` clears every reference-bearing field. The `__DEV__` heuristic catches retained objects but not stale scalars. Identical in probe 1.

### F-12 — teardown crosses two owners · resolved by contract

`spec.retire()` may throw, and it runs while the behavior's DOM is still attached. Both are addressed by the normative seven-step order in §[01](01-construction-ownership.md): the kernel wraps `retire()` in try/catch/report/continue, and `retire()` drops references while the _presentation lifetime_ releases DOM.

### F-13 — the landing target goes stale under a concurrent authored commit · confirmed, resolved

Established by the React probe. A frozen `CollectionSnapshot` freezes the semantic transaction; it says nothing about layout. An authored commit that inserts, removes or resizes content above the placeholder moves the placeholder's viewport rect while landing is running.

Resolved by D-16: the target measured at settlement entry is explicitly **provisional**, and the kernel re-measures and pins authoritatively at the join before releasing presentation (I-24).

### F-14 — React repositions or detaches the injected placeholder · disproved

The probe establishes that React does **neither**. The placeholder is an unmanaged sibling in a reconciled container and survives commits in place. This finding is withdrawn; the earlier speculation that it might require abandoning the injected-placeholder strategy is not supported.

### F-15 — the placeholder can end up in the wrong semantic gap · confirmed, resolved

A _new keyed item_ inserted into the destination gap by the authored commit leaves the placeholder on the wrong side of it. The placeholder's position is still physically where we put it (F-14), but it is no longer the correct _semantic_ gap.

Resolved by D-16's re-anchor: ~~at readiness, and defensively again at the join~~ **at the join, once** — D-41 collapses the two sites into one authoritative measurement, so the defensive repetition has nothing to defend against — the behavior runs the guarded equivalent of `item.before(placeholder)`. The probe establishes that the repaired placeholder rect equals the dragged item's actual landed rect after teardown, and that the repair is inert in the already-correct cases.

The guard is required, not optional: `Node.before()` on an already-correct position is a remove-and-reinsert, which resets CSS transitions on the placeholder and forces a reflow.

```ts
if (placeholder.nextElementSibling !== item) {
  item.before(placeholder);
}
```

### F-16 — a late readiness correction can be visually abrupt · ~~accepted, quality only~~ · scenario superseded by D-41, classification inherited by D-49

**The scenario can no longer occur, and the classification it established is the one D-49 reuses.** The original finding follows, because the reasoning is what carries forward.

~~When a short landing completes _before_ readiness, the provisional trajectory has already finished, and the authoritative correction at the join is a visible step rather than a smooth arrival.~~ Under D-41 there is no readiness, no provisional trajectory and no second measurement: the landing opens from a target measured once, authoritatively, after the authored commit. There is nothing to correct late, so the abrupt correction this finding accepted is **unconstructible** rather than merely rare — and `LandingHandle.retarget` is removed in §[02](02-kernel-behavior-contract.md), so the paragraph below about when it is not called describes an API member that no longer exists.

~~Correctness is unaffected (I-24 holds in both completion orders — the probe tested both and got the same authoritative pinned target). A retargetable runner smooths it; the kernel guarantee does not depend on one, and `retarget()` stays optional for exactly that reason.~~

~~In precisely this case `retarget()` is **not** called: the readiness path is guarded on `attempt.landingHeld`, not on the handle, which is deliberately retained past its gate release so the join can `destroy()` it. **What survives is the tiering, and D-49 is where it lands.** This finding established that a visibly imperfect arrival is a **quality** matter and not a correctness one — that the library may look briefly wrong without being wrong, and must not escalate that into a classified failure. D-49 applies exactly that judgement to the case D-41 created: a measurement that cannot be trusted **skips the landing animation and joins immediately**, which is a jump cut. A jump cut is this finding's abrupt arrival by another route, accepted on the same grounds. **The inversion is worth naming**: here the abruptness was the price of correcting a target the library did not yet trust, and there it is the price of declining to animate toward one — probe C1 shows the alternative, a confident 12-frame flight to the viewport origin followed by a teleport back, and that is the case where looking right and being right come apart. A jump cut is honest; a confident animation to `(0,0)` is not.

`anchorTarget()` at readiness and `retarget()` are both fallible, and neither is load-bearing: the join re-measures and pins authoritatively regardless. Treating either as a classified failure would settle the operation with `OUTCOME_FAILED` over a blip the very next step is about to correct.

Both are therefore **best-effort reports** — the platform reporter, the same channel as a failing disposer — with the landing left running, holds untouched, and `attempt.authoredReady` still set. Only the join's measurement is classified (`FAILURE_LANDING_TARGET`), and even that releases presentation rather than stranding the controller. The full table is in §[02](02-kernel-behavior-contract.md) §Failure on the quality track.

**Revision 2 keeps this finding's answer and replaces both of its subjects (D-49).** Readiness-time `anchorTarget` and `retarget()` are gone — the first with the readiness gate (D-41), the second removed from the SPI in §[02](02-kernel-behavior-contract.md) — and `attempt.authoredReady` with them. The quality path still exists and still throws: it is now the **single authoritative measurement**, and D-42's precondition check is a second way for it to come back untrustworthy rather than a different kind of failure. The response is this finding's response, one step further: report through `onError`, and because there is no second site to correct a bad target, **skip the landing animation and join immediately** instead of animating toward it. The settlement is not failed, the domain result is unchanged, and the reasoning is the one stated above — treating it as a classified failure would settle with `OUTCOME_FAILED` over a presentation blip, and now there is not even a blip to justify it, because nothing is animated.

### F-18 — a post-commit effect can leave a visible unowned resource · resolved by contract

`prepare` has `rollback`; `effect` does not. An effect that inserts the placeholder and _then_ registers its removal leaves a window where a throw produces a visible orphan the presentation lifetime does not own.

Resolved by I-30's ordering rule. Registering first is free, because removing a detached node is a no-op — an over-eager disposer can never over-release.

### F-19 — the generic transition driver was not total · resolved by contract

One driver was shown for every seam, but four callers needed something it did not provide: an `effect` throw escaped to panic instead of being classified; a `rollback` throw had no policy; an activation discard needed seam-specific retirement; and the activation trace performed a post-effect `preparationValid()` the driver did not have.

Resolved by keeping one **core** and giving each seam its own wrapper with its own discard and failure policy (§[02](02-kernel-behavior-contract.md) §The shared core). Two of the four discards stopped being expressible at all.

### F-20 — legal `null` returns could strand an operation · resolved by types

`release.prepare` returning `null` left a truthful but stranded `RELEASING` operation: no resolution, no failure, no retirement. `settlement.prepare` documented `null` as "after queueing a failure", which the kernel could not verify once the resolution payload was consumed.

Both are now non-nullable. Release stages a `ResolutionCommand`; settlement returns `PreparedSettlement | SeamRejection` and the kernel classifies the rejection itself. The `ResolutionGate`'s `open`/`skip` linearity problem disappears with it — the choice became a value.

### F-21 — synchronous landing completion raced the hold · resolved by contract

A `duration: 0` or custom runner can call `done()` from inside `start`. With the hold installed _after_ `start` returned, that completion was either dropped (stranding settlement) or applied against a half-built attempt.

Resolved by _request → seal → arm_: holds are reserved during `settlement.effect`, the plan is sealed, and only then is the watch armed and the runner started. The handle is published before any queued completion can be applied. A `start` throw rolls the reserved hold back.

### F-22 — cleanup was not robust across code the kernel does not own · resolved

The join calls a behavior measurement, a possibly-custom `LandingHandle.destroy()` and a lift write, then releases presentation — and any of the three could skip the pin _and_ strand temporary presentation. Feature retire hooks had the same shape: a plain array, with only the outer `spec.retire()` wrapped.

Resolved by putting presentation disposal in a `finally`, making runner destruction a best-effort report, classifying the pin failure without letting it prevent release, and wrapping each retire hook individually in reverse installation order.

### F-23 — long-lived `fail(stage, error)` could fail the wrong operation · resolved

`fail` targets whichever operation the kernel currently holds, so a late asynchronous callback belonging to operation A could classify a failure against operation B — contradicting the double-validation rule everything else obeys.

Resolved three ways: seam throws are caught and classified by the driver; the kernel's `inSeam` latch downgrades an out-of-seam `fail` to a platform report; and the long-lived `FeatureContext` carries `report(error)` instead of `fail`. `stage` is also a closed `FailureStage` union rather than a bare `number`, so a participant cannot forge a kernel-private stage.

### F-24 — hot-path accounting was internally inconsistent · withdrawn and restated

The trace claimed "zero allocations, two indirect calls" and then, two lines later, acknowledged the transform string. The shown path also makes three calls, not two (`spec.moved`, `lift.write`, `rt.frame.schedule`), and the shipped in-place lift mode allocates a `{ x, y }` projection (`packages/drag/src/kernel/presentation.ts:190-224`).

The headline is withdrawn rather than defended. I-26 is restated as something measurable, and the falsifier that referenced it is gone from §[00](00-index.md). See §[06](06-vertical-sortable-trace.md) §The hot path for the counted version.

### F-25 — the reentrant-cancel counterfactual reversed FIFO · corrected

The trace claimed that a `cancel()` called from inside `onReorder` loses because `RESOLUTION_SETTLED` is already ahead of it. **That is backwards.** The resolution command must invoke consumer code before it can obtain a value to settle, and a nested `dispatch` appends in call order — so `cancel()` enqueues _first_, and `RESOLUTION_SETTLED` can only be enqueued after `onReorder` returns. **The cancel wins; the later completion is stale.**

The shipped package confirms the order: callback invocation at `packages/drag/src/sortable/runtime/actions.ts:925-950`, settlement dispatch at `952-964`, cancellation dispatch at `1450-1477`.

This is the concrete example of `CANCEL > FAILURE_CHECKPOINT` and FIFO working as specified, not an exception to them, and it is now an explicit test rather than a counterfactual row.

### F-27 — classification did not stop incompatible continuation · resolved

The core driver returned a `boolean`, conflating _discarded_ with _failed_. Every caller then continued success work between a classified throw and the queued failure checkpoint: activation retired the operation out from under its own `FAILED` entry, release invoked `onReorder` after its effect threw, settlement armed a half-requested gate plan, and the join called `finalized` — emitting `onFinish` for a drop the checkpoint was about to report through `onError`.

Resolved by `SeamOutcome` and a stated continuation rule per seam (§[02](02-kernel-behavior-contract.md) §The core returns an outcome). **F-19 was not actually resolved before this**: catching a throw is only half of a failure model.

### F-28 — an invalidating collection replacement was discarded · resolved

The invalid paths called `host.cancel(reason)` and returned `null`, which skips `effect` — so the cancellation landed but the consumer's collection update was thrown away, and the next press started against stale items.

Resolved by staging `cancelReason` in `PreparedCollection` and dispatching it last from `effect`, after publication. An invalid collection ends the current drag; it does not un-happen the update that ended it.

### F-29 — settlement status had no total mapping · resolved

Five open statuses, no exhaustive mapping to outcome, recovery, domain result, callbacks and failure stage — so the reference behavior mapped every non-fulfilled status to rejection with home recovery, turning a semantic **no-op into a rejected drop** that animates home and calls `onCancel`.

**One cell of that mapping is no longer a gap, and D-60 requires it to be expressible rather than absent.** The `FailureStage` → recovery mapping must be able to state **classified, no recovery, not consequential** as a _member_ of the mapping: `FAILURE_LANDING_TARGET` under D-49 is the first stage that occupies it — the failure is classified and reported, no recovery is chosen because the drop is not being recovered from, and the settlement is not failed. A mapping that treats "no recovery" as a hole reintroduces exactly this finding's defect one level up, by forcing a stage with nothing to recover into some other stage's recovery.

Resolved by a discriminated `SettlementInput` covering all five cases — fulfilled, rejected, skipped, canceled and failed — with an exhaustive mapping to outcome, recovery, domain result and callback. `OUTCOME_NOOP` prevents a semantic no-op from becoming rejected/home. A rejected thenable is a named classified failure rather than an inferred consumer verdict. The temporary three-case version was withdrawn by F-33: cancellation/failure are kernel- triggered, but the terminal domain fields they produce are behavior-owned.

### F-30 — a resource returned from a reentrant callback could leak · resolved

Reserve-before-call protects resources that already exist. It does nothing for a resource the callback _returns_: a `LandingStart` that synchronously destroys the controller and then returns a live handle left that runner owned by nobody, on a retired attempt. The same hole existed at admission, where a consumer resolver can `destroy()` during native dispatch and the listener carried on to mint an operation.

Resolved by post-callback revalidation at both ends, with immediate best-effort destruction of a stale returned handle — and stated as a general rule rather than two patches.

### F-31 — the placeholder writer could not express a start gap · resolved

The reference moved the placeholder with `insertion.before?.after(placeholder)`, which is a silent no-op when `before` is `null` — so the placeholder could never reach the head of the list. `homeInsertion` compounded it by producing `before: null, after: null` regardless of the item's real neighbours.

Resolved by one canonical `movePlaceholder()` used by both the action and release effects (anchor on `after`; append when it is `null`), and a `homeInsertion` that carries real identity neighbours. Keeping one writer also protects the non-oscillation rule from divergent implementations — and gives the cross-container refusal a single home: the writer rejects an anchor whose parent is not the placeholder's, so a reparented item cannot silently relocate the footprint out of the list (D-27).

### F-32 — the `ACTIVATING` collection deferral contradicted FIFO · resolved

The table claimed an update arriving during `ACTIVATING` was queued behind the activation checkpoint. It cannot be: `onStart` runs before `START_COMMITTED` is dispatched, so an `updateItems()` from inside it is appended first and FIFO runs it first.

Resolved by **deleting the deferral**. I-30 already publishes `rt.view`, `rt.placeholder` and `rt.lift` before `onStart`, so an `ACTIVATING` frame is as reconcilable as an `ACTIVE` one. No pending slot, no requeue, no anti-spin rule.

**`updateItems()` is itself removed by D-44 (Revision 2), and this finding survives the rename intact.** Collection delivery becomes a pull source plus a payload-free signal — `sortable({ items: () => … })` supplies the current committed collection and `controller.invalidate()` says it may have changed — with **array identity as the structural test**: the same identity invalidates geometry only, a new identity triggers snapshot, reconcile and geometry invalidation, and the library's shallow copy happens only on that branch. Read every `updateItems()` in the narratives and the matrix below as `controller.invalidate()` reaching the same collection action; the FIFO argument is about _when the action is queued relative to `START_COMMITTED`_, which is unchanged by what produces the payload. In-place mutation of the same array is outside the contract, and no `itemCount()`/`itemAt()` scanning protocol replaces the removed method.

The invalidating case then has an ordering of its own: the cancel is raised by the collection action's _effect_, so it is queued **behind** `START_COMMITTED` rather than ahead of it. `START_COMMITTED` consults the latch and declines to advance, leaving the phase at `ACTIVATING` for the cancellation to settle (§[02](02-kernel-behavior-contract.md) §I-31). Without that check the operation would activate for exactly one drain and report the cancellation from `ACTIVE`.

### F-33 — kernel-owned cancel/failure could not build behavior-owned state · resolved

Removing `canceled` and `failed` from `SettlementInput` created an ownership hole. `outcome`, `recovery` and `domain` are fields of the **behavior's** frame part, which the kernel cannot name or write, and `BehaviorSpec` has no other terminal-classification hook — so a kernel `CANCEL` could commit `SETTLING` and then had no way to produce the canceled result `onCancel` requires, and the failure path could not choose a behavior-owned recovery.

**Ownership of the trigger and ownership of the resulting domain state are different things.** All five cases go back to `settlement.prepare`, discriminated and exhaustively mapped (§[02](02-kernel-behavior-contract.md)). The original defect was the open numeric status and the missing mapping, not that the behavior classified behavior-owned state.

### F-34 — `host.fail()` bypassed the seam outcome · resolved

`SeamOutcome` covered _throws_. A seam that classified without throwing — `host.fail(stage, e); return normally;` — still returned `SEAM_COMMITTED`, so every continuation D-23 forbids ran anyway.

Resolved by a kernel-private `seamFailureRequested` latch, cleared as each seam phase opens and set by `host.fail`, making an explicit classification indistinguishable from a throw at the driver boundary. Enqueuing a checkpoint was never sufficient: the checkpoint is queued, and the window before it applies is exactly what the latch closes.

### F-35 — a landing-create failure still finalized the original settlement · resolved

An arm-time `anchorTarget` or `start` throw was classified, rolled the landing hold back, and continued the settlement. With readiness also open the hold count reached zero and the **accepted** settlement finalized — calling `onFinish` — before the queued failure checkpoint ran.

Resolved by `ArmOutcome` (`ARM_ARMED` / `ARM_STALE` / `ARM_FAILED`). `ARM_FAILED` suppresses `advanceSettlement` and every terminal callback for the replaced settlement. A once-only completion latch on the attempt makes the synchronous `fail()` case work too: it sets `failed` before `start` returns, so the returned handle is destroyed and never published.

### F-36 — `destroy()` was not total across a throwing frame reset · resolved

Teardown wrapped attempts and `spec.retire()` but called `spec.resetFramePart` twice unwrapped. A throw on the first frame could skip the second scrub and the ingress abort, leaving `destroy()` non-terminal against I-6.

Each scrub is now individually best-effort and ingress abort runs from a `finally`. The reset error is reported and never substitutes for the initiating destroy or panic error. The same rule applies to the `arm()` unwind.

### F-37 — the terminal callback used a binary outcome predicate · resolved

`finalized` sent `OUTCOME_ACCEPTED` to `onFinish` and _everything else_ to `onCancel` — so the no-op result that D-24 exists to distinguish went to `onCancel`, reintroducing the exact semantic error at the terminal boundary.

Replaced with an exhaustive switch on the domain result's discriminant. Accepted and no-op finish; rejected and canceled cancel; ~~failed produces no domain result and never reaches `finalized`~~ — **retracted by D-66: a failed settlement now builds a `canceled` result in the seam that receives `SETTLED_FAILED`, so `finalized` finds a result where it used to find `null`.**

**Revision 2.1 removes the mechanism rather than the bug (D-62).** With one `onEnd` taking the whole four-arm union there is no predicate and no routing: the library hands the result over and the consumer's own `switch (result.type)` is what the compiler checks. This class of defect — a four-arm result compressed into a two-way branch — is no longer expressible at this boundary. **The `failed` clause did not survive**: _"never reaches `finalized`"_ is retracted by D-66 — a failed settlement now reaches `finalized` and publishes `canceled`, carrying the classifying error as its `reason`. F-37's own fix is untouched by that: the switch is still on the domain discriminant, and the failure path simply supplies one where it previously supplied none.

**D-60 tests this fix and it holds, for a reason worth making explicit.** The switch is on **the domain result's discriminant**, never on whether an error was reported — so an operation that reports through `onError` and still has a domain result routes on the result, exactly as it should. That is precisely the case D-49 creates: a landing measurement that cannot be trusted is classified `FAILURE_LANDING_TARGET`, reports, skips the animation, and **the settlement is not failed**, so the domain result stands and `finalized` runs normally. **Read "failed produces no domain result" as the settlement's `failed` case, not as "a classified failure occurred"** — the two were coextensive until D-49 and are not any more. Had the fix keyed off a failure flag instead of the discriminant it would now be wrong; keying off the data is what makes it survive a decision taken years of review later.

### F-38 — the arm path could call `start` after a synchronous destroy · resolved

Revalidation existed _after_ `LandingStart` returned but not after the `anchorTarget` immediately before it. `anchorTarget` is behavior code and can synchronously `destroy()` the controller, after which the kernel called the consumer's runner anyway — violating I-6's "no callback fires afterwards". Destroying the returned handle later does not un-call it.

Resolved by revalidating on both sides of `start`.

### F-39 — the final pointerup sample was rendered only in the trace · resolved

The trace rendered the lift at the committed release point; the normative seam table, the release pseudocode and the reference behavior moved only the placeholder. Since `pointerup` need not share coordinates with the last processed `pointermove`, following the seam table would compute the proposal from the final point while the visual and the landing trajectory started from a stale one.

The final render is now part of normative `release.effect`, classified `FAILURE_RENDERER_WRITE`.

### F-40 — `moved()` had no failure policy · resolved

`moved` is not a transition and had no wrapper, so a compose, CSSOM or `schedule` throw escaped the handler and became a **panic** that destroyed the controller — contradicting the existence of `FAILURE_RENDERER_WRITE` and `FAILURE_SCHEDULED_FRAME`, and diverging from the shipped implementation.

The kernel now wraps it (`FAILURE_RENDERER_WRITE`). Rendering and scheduling stay one callback with two stages, narrowed from the inside via `host.fail(FAILURE_SCHEDULED_FRAME, …)`, because splitting them would add an indirect call to the one path that counts them — and the failure latch makes the narrowing visible to the driver.

### F-41 — the public proposal and result types regressed · resolved

The fixture had reduced the proposal to `{ from, to }` and aliased both result types to one numeric record, dropping probe 1's identity neighbours, proposal version and cancellation detail — and exposing an outcome constant the export table declared internal.

Restored as narrowed unions with string discriminants, and `CancelStage` (`AT_PROPOSAL` / `AT_CONSUMER`) is public.

### F-42 — the feature-authoring boundary was internally contradictory · resolved

`SortableFeature` was declared public and stable while being _defined_ as a function between two types declared internal and unstable, so any change to either changed the public type's assignability and emitted declaration.

Resolved by making the feature value **opaque** (an unexported `unique symbol` brand). Nameable and passable, not constructible — so the closed world is real rather than aspirational, and the authoring types are genuinely internal. The same leakage in `DragErrorContext` and `LandingContext` was resolved the other way, by exporting `FailureStage` and `DOMRealm`, which consumers legitimately need.

### F-26 — the tree-shaking criterion named an impossible minimal build · corrected

`vertical()` is required, and the criterion demanded "axis geometry" be absent from the minimal build. A minimal _vertical_ sortable necessarily contains vertical axis geometry.

Corrected in §[03](03-feature-composition.md) §Tree-shaking: the minimal fixture is written out exactly, and what must be absent is _unselected_ geometry (horizontal, grid), free drag, landing and layout animation — which is what the brief actually asks for (`brief.md:615-637`). The subpath/export table and the `files.json` consequence are now written down too, because the shipped package exposes only `draggable`/`sortable` entries and a new topology cannot be measured before it is specified.

### F-43 — the SPI had no route for discrete input · resolved by D-32

Probe [13a](../probes/13a-discrete-input.md), four compile-proved negatives: `admit` takes a `PointerEvent` and `BehaviorSpec` has no second admission member; `KernelHost` owns no extensible ingress; `dispatch` returns `void`; nothing mints an operation without a press. The load-bearing one is the third — the others have workarounds that are merely ugly, and that one has none, because the information flows the wrong way through the only behavior-initiated entry that exists.

Four runtime facts came with it, none of which typecheck can see: one ingress listener exists and it is `pointerdown`; `admit` has one call site, reached only from `onPointerDown`; `PENDING → ACTIVE` is a pointer-distance test, so a command admitted as a press would sit in `PENDING` forever; and the frame gates every sample on `pointerId`. Together they are why a command is **not** "a press with no moves".

Resolved by D-32: a second admission member, a redefined `PENDING`, and `pointerId === -1` made normative for a pointerless operation. What it did _not_ need is the thing 02 had been declining to reserve — a behavior-to-kernel lifecycle-intent protocol. The gap was that a behavior could not be **asked** a question synchronously, not that it could not **ask** for a transition.

### F-44 — activation staged type pinned to `HTMLElement` · resolved by D-34

Probe [13c](../probes/13c-free-drag.md) N-1. `BehaviorSpec.activation` was `Transition<Part, HTMLElement, ActivationScope>`, and the only other inhabitant of that return type — `null` — already means _discard the activation_. A behavior that stages nothing at activation had no honest value to return; the probe returns `scope.visual`, an element the kernel already holds, and its `effect` must then ignore what it is handed. That is the staged-resource contract inverted.

The sortable's shape written into the kernel, and one type parameter wide.

### F-45 — the landing origin was a pointer delta · resolved by D-35

Probe 13c N-2. `LandingContext.from` was `pointerX - originX`, documented as "where the visual is now". True for exactly one behavior. Any behavior that constrains, clamps, snaps or externally drives its visual has written something else, and under D-32 a pointerless operation has no pointer at all.

The failure signature is the one this project has already met once: **the landing opens with a jump and ends correctly**, because the target is behavior-supplied and the kernel re-pins at the join. Phase 11 found the same shape in the lift geometry, with every test green throughout, and only a demo exposed it.

Resolved without a seam: the lift session records the delta it wrote, and the kernel reads its own object. 13c's compile assertion — that no `BehaviorSpec` member reports the rendered delta — deliberately **still fails to compile**.

### F-46 — the authored-presentation protocol distributed its burden badly · resolved by D-33

Probe [13b](../probes/13b-settlement.md) B-1. Four obligations on the consumer, whose failure modes are a 500 ms silence and, for a hold never taken, nothing at all. **Inherited from the shipped package** — the identical `createCommitTracker` is in both packages' story files — and **not a correctness defect**: every shipped and ported story works. It is a distribution-of-burden defect with two bad failure modes, which is a sufficient basis for a revision and is not the same claim.

Resolved by D-33: the resolution **declares** an authored presentation, the controller **acknowledges** it, and the request is the identity. The property that had to survive is stated by this document and did: the two gates are independent and nothing awaits, so the authored re-render still overlaps the landing animation. A design that lost the overlap would not have been a simplification.

**The first attempt at this resolution was wrong, and the failure is the instructive part.** Phase 14 initially chose 13b's candidate C-2 — a kernel-minted token delivered while the settlement armed. Checkpoint C found two defects, both tracing to one root: a capability minted by the settlement is **younger than the render it acknowledges**. A synchronous commit therefore acknowledged nothing and timed out (C-01), and the `abandon()` state the design needed produced an accepted `onFinish` over an authored DOM still showing the old order (C-02). The request has the opposite age by construction — it is the argument to the callback that _asks_ for the render — which is why C-3, rejected in 13b for lacking identity, is the design that works once you notice the identity was already there.

**F-6's status improves and is not promoted, and the follow-up review made the line sharper.** Obligations 1 and 2 leave the consumer, and a stale acknowledgement becomes diagnosable rather than silent. Three of the four consumer error modes are now loud: declaring without acknowledging hits the deadline, and acknowledging without declaring is **reported** — a declared contradiction the kernel can see without inferring anything from DOM mutation.

The fourth is not, and an earlier draft of this section implied otherwise. `{ presentation: true }` is **opt-in**: a consumer that declares nothing and then renders asynchronously has entered neither half of the protocol, and is indistinguishable from one that legitimately rendered synchronously. That is **probe 13b's R-2 shape surviving**, at tier C. Flipping the default was considered and rejected — it converts the legitimate imperative consumer into a 500 ms stall and a classified failure (02 §Absent means _already final_).

So F-6 keeps its test obligation and gains a second clause: any fixture that renders asynchronously must **declare** as well as acknowledge, and the witness in `tests/support/gates.ts` fails loudly if the corresponding hold is never taken. I-35 is worded against exactly this table and claims nothing beyond it.

**Revision 2 resolves F-46 by deletion (D-41), and that is the stronger resolution this narrative was reaching for.** The paragraphs above are the record of a protocol being made as good as a protocol can be; D-41 removes the window the protocol existed to cover. The order becomes serial — _release → freeze proposal → `onReorder` → authored commit → consumer resolution → restore library presentation invariants → authoritative landing measurement → landing → terminal_ — so a consumer that renders asynchronously simply **`await`s its own commit inside `onReorder`**, which a Promise-returning resolver already expresses with ordinary failure behavior. All four obligations go with the protocol: there is nothing left to declare, acknowledge, mismatch or forget.

**Read the paragraph above about obligation 3 in that light.** It called the fourth mode irreducible, and it was — _given a protocol_. An opt-in declaration that a consumer can simply not make is undetectable by construction, and flipping its default breaks the legitimate synchronous consumer; both halves of that dilemma are real and neither has an answer inside the design that poses it. Deleting the acknowledgement deletes the dilemma rather than solving it, which is why D-41 is admitted to the frozen set as a **deletion** and needs no failing executable case: a deletion cannot be something the SPI fails to express. What survives of F-6 is first-party only — a behavior that installs `landing()` and never takes the corresponding hold — and stays a test obligation for the reason it always was: sealing detects a _late_ hold and never a _missing_ one.

**The property this document said had to survive did survive, by a different route.** The two gates were independent so that the authored re-render could overlap the landing animation; with readiness deleted there is nothing to be independent of, and the overlap is not lost but relocated — the commit now completes _before_ the authoritative measurement rather than racing it, which is what probe C1 showed was necessary anyway, since `authoredReady` is false at `armSettlement` by construction and the provisional target was stale in all five commit strategies.

### F-47 — the terminal barrier stopped at the seam boundary · resolved by I-36, re-scoped by D-37

**Read this section with its halves separated, because Revision 2 keeps one and withdraws the other.** The **defect is real and its fix survives at the floor**: a participant that calls consumer code repeatedly inside one seam or one native admission reads the latch between calls, and every narrative below describing _how the sites were found_ stands as the review record. What is **withdrawn** is the ceiling half the fix grew afterwards — the promise of no further geometry read at all, and the whole-program enumeration that tried to discharge it — because D-36's transaction bracket undoes every act in that half at the boundary and D-37 replaces the domain with the finite one (a)/(b)/(c). Concretely: the barrier table below stays as the historical record of the search; its rows that name a **declared consumer slot** are still normative through I-36 (a), and its rows that name an overridable platform member on a consumer-owned node are **no longer obligations**. Probe A measured which is which — four irreducible sites, all act (a).

Found by Checkpoint D review 2 (C2-01), reproduced against the restored D2 geometry path. `RectIndex.refresh` loops over the destination view and calls the consumer's `visual()` resolver once per candidate. A resolver that calls `controller.destroy()` runs teardown to completion synchronously and returns; **the loop then continued**, resolving every later candidate after `destroy()` had returned — the synchronous terminal barrier I-6 forbids crossing, at the tier-C half of it I-36 now names.

**The reported half was the smaller one.** `destroy()` step 4 runs `spec.retire()`, one of whose hooks _is_ `index.retire()` — emptying `items`, zeroing `count`, setting `dirty = true` and `measured = -1`. A continued traversal writes elements back into `index.items` and its trailing bookkeeping then sets `count = n`, `items.length = n`, `measured = version`, `dirty = false`. So it does not merely call a consumer callback late: it **resurrects a cache teardown has retired**, marks it clean, and leaves an idle destroyed controller pinning every row of the list against I-20, through the one field `retire()` exists to clear. This is why the fix restores the retired state rather than `break`ing, and why the tests assert a rebuild-from-scratch at the same snapshot version.

**Two more sites of the same species, one of them unreported.** `resolveItem` calls `getHandle` and `seedDraft` then calls `getVisual`, with nothing between them; and `action.effect(TAG_SPATIAL)` runs a placeholder custom element's `disconnectedCallback` synchronously inside `movePlaceholder`, then an eager cache rebuild and every `afterMove` hook — which with `layoutAnimation()` composed starts WAAPI animations on a torn-down controller. `activation.effect` already guarded the _identical_ hazard one line after `item.after(placeholder)`, with a comment naming I-6; the spatial bracket is the same hazard through the other door.

**The root reading, and the reason this is an invariant rather than a patch.** D-26 stated post-callback revalidation as a rule about values the kernel **receives**; it was never stated for sequences a behavior **drives**. Every gap in the enumeration below is a sequence the behavior drives, and that generalizes to any behavior that calls consumer code more than once inside one seam or one native admission — which is why Phase 18 carries an explicit deliverable to enumerate free drag's consumer callbacks and state where each one's terminal barrier is, rather than rediscovering this at Checkpoint E.

**The enumeration was incomplete twice more, and the second correction is the one that changes its shape** (Checkpoint D reviews 3 and 4). C3-01 found that the barrier stopped _reporting_ — the traversal aborted but the axis went on to measure the consumer-owned placeholder — and C4-01 found the barrier itself sitting one indirect call too early: the check stood between `getVisual` and the candidate's own `getBoundingClientRect()`, and that read is a consumer call under I-36's indirect-invocation clause. A destroy raised from it fell through to the cache write, to the next candidate's resolver, and — on the **last** candidate — to the trailing bookkeeping that marks a retired cache clean. It reaches a composition that installs no `visual()` at all, because there the item is its own visual.

**Three consecutive passes each found one more site, and the reason is stated here so the fourth does not repeat it.** The rows below were derived by asking "which consumer callbacks does the library invoke", and the answer under the indirect clause is a different and larger set: **every DOM method the library calls on a consumer-owned node**, because any of them can be overridden on a consumer's custom element. Enumerating those one at a time does not terminate, and that is why I-36's clause became a floor plus a register at review 4 rather than gaining a fourth site. At review 5 it gained the second discharge form the table above had carried since C2-01 — a kernel bracket that revalidates and undoes — and lost the word "complete", because two of the sites the fifth review found were at modules that already held readings (C5-03). So C4-01 places the barrier structurally instead — at the **head of every loop that touches consumer-owned nodes, after each consumer-reachable call inside it, and before the next foreign call, DOM mutation or state publication** — and the table below records the result per site rather than per callback name.

**One residue, classified at review 4 and discharged at review 5, and the reason C4-01 left it open was wrong on the facts.** `landing()`'s `duration` thunk is consumer code called inside `LandingStart`, and the next statements reach the consumer's own visual — `realm.window.matchMedia`, then `visual.animate()`, then the `finished` accessor and `then` — with no reading between them. C4-01 recorded this as a `LandingContext` question and therefore a frozen-SPI question. **It is neither**, and review 4's correction of that fact stands: `FeatureContext` (`src/sortable/feature.ts`) is behavior-owned, is constructed by the behavior at `src/sortable/behavior.ts`, is exported from no entrypoint, and already carries a behavior-supplied closure — `report` — for the same reason a liveness reading would be one. What review 4 got wrong was the _classification_: it called provisioning universal, named this module as not provisioned, and then declared the site conforming under the floor, whose antecedent does not engage where no reading exists (C5-03). **The site is discharged, not excused.** The whole stretch is bracketed: before publication F-30's `!settlementLive(attempt)` branch destroys the unpublished handle, and `destroy()` on it is `generation += 1; animation.cancel()`, which removes the effect including the forwards fill inside the same synchronous stretch with no style flush and no rAF; after publication `retireSettlement` disposes the published handle the same way, which is what covers `retarget`'s `getComputedStyle` → `cancel()` → `animate()` sequence too. Nothing is published, nothing is retained, no mutation survives, no declared callback is invoked by the feature, nothing is dereferenced — and the landing never starts. **The bracket-discharge falsifier, which replaces review 4's trigger list**: any consumer-reaching stretch inside `start` or `retarget` whose effect the bracket does not undo — a publication, a retained reference, a mutation on a node the library did not adopt, or a continuation that outlives `start`'s return. On any of those `landing.ts` must hold a reading, and **`FeatureContext.live()` is the available shape**: a sixth additive widening of a behavior-owned internal type, measured at **+6 B to +53 B** brotli, costing no frozen SPI and no public surface. It is **not queued** — it would install a `rt.closed` reading blind to a `panic()` destroy beside a kernel bracket that sees one, and would spend half the tightest composition's headroom on defence in depth while floor breaches are open. Widening `LandingContext` instead would be both an SPI change and an addition to the **frozen public surface**, and is rejected on that ground independently. One ordering constraint for whoever ever takes it: `assemble()` runs before `rt` exists, so the closure is late-bound and a feature factory must not call it at construction, which the "externally inert" factory rule already forbids. **Superseded by D-37, and preserved because the argument is the one D-37 generalises.** Review 5 discharged this site by showing that a named kernel bracket which revalidates _and undoes_ is the stronger discharge where it applies; D-36 makes that bracket universal rather than site-specific, so the whole of this paragraph's reasoning now holds everywhere and stops being a per-module verdict. The 'bracket-discharge falsifier' stated here survives in exactly one respect and is worth carrying: a stretch whose effect the boundary does **not** undo — a publication, a retained reference, a mutation on a node the library never adopted, or a continuation outliving the transaction — is still the shape that breaks the model, and D-39's placeholder rollback is the first confirmed instance of the third case. **`FeatureContext.live()` is therefore not queued and not needed**: the reading it would have installed is one of the 27 D-37 retires.

**~~What is not closed.~~ Closed by D-36, and the closure is a reordering rather than a new mechanism.** Original text follows, because the reachability argument in it is still the live one and only its conclusion changes. ~~A `panic()`-initiated `destroy()` does not set the controller's latch, so the three sites reading it do not see one.~~ Under D-36 `panic()` follows the same model as `destroy()`: it **closes logically first, then reports, then tears down**. The latch is therefore set for a panic exactly as for a consumer destroy, and the gap this paragraph recorded is gone — which is what makes I-37's rule affordable, since the abort signal's one advantage over the latch was that it saw a panic the latch did not. The argument that a kernel-internal destroy is unreachable from inside a resolver is _reachability_, not a type property: a throw from consumer code inside a seam is caught and classified rather than panicking, a nested `dispatch` enqueues without draining, and no consumer callback opens a seam — so the only destroy a resolver can cause is `controller.destroy()`. If a future path makes a kernel-internal destroy reachable from a resolver, that is an SPI question and must be argued as one. The stated falsifier for keeping the latch behavior-owned is a **third** behavior needing its own copy; two behaviors sharing a two-line idiom is not duplication worth a frozen-surface change.

**Probe A verified the reachability argument structurally, and found it stronger than a reachability argument usually is.** Enumerating every `spec!.*` call site in `src/kernel/kernel.ts` shows each one sits inside a seam phase (`runPhase`), a `runLeaf`/`runLeafValue`, or a `guarded`. The documented producer — `refuseReentry`'s latch, rethrown past every classification by `runPhase` — needs a **nested seam**, which the run-to-completion queue forbids outright, because a nested `dispatch` appends and returns. So **`panic()` has no producer reachable from behavior or consumer code**, and the probe had to manufacture one: **the single unwrapped foreign read left on a queue handler**, `spec!.config.threshold`, consulted by `handleMove` outside any seam. That unguarded read is recorded here as a known site — it is the one place a consumer accessor can reach `panic()` today, and anyone adding a second unwrapped read on a queue handler is widening this surface. **Two consequences follow, and they point in opposite directions.** `panic` is reached from `drain`'s `catch`, _after_ the loop has exited, so the deferral window is one stack frame wide and its only statement is `report`, which touches no library state — no library code runs after the unexplained throw, and no physical teardown runs on the broken stack. Observed as the teardown order flipping from `['retire','report']` to `['report','retire']`. But the safety of reading the logical latch at those sites **depends on the throw having already unwound the stack**: a future kernel path that panics _without_ unwinding would leave a behavior with no reading at all, which is the argument for exposing the kernel's logical latch on `KernelHost` if such a path is ever created, and against creating one.

### The sortable stretch table — retired as a proof domain (D-37, Revision 2)

**What it was.** Checkpoint D review 5 (C5-03 §7 and §8) swept `src/sortable/*.ts` statement by statement and enumerated every **consumer-reaching stretch** — a maximal run of a module's own statements beginning at a consumer-reachable call and ending at the next liveness reading, the return into a kernel bracket that revalidates, or the module's return — where a _consumer-reachable call_ included any overridable accessor on a consumer-owned node (`isConnected`, `offsetWidth`, `style`, `animation.finished`), not only a declared slot. One question per stretch: does anything the stretch does survive the stretch? Each row carried one of three verdicts — **(a) reading-headed**, **(b) bracket-discharged**, **(c) conforming residue** — and no row was (d). The result was **twenty modules, 62 stretches — 38 (a), 6 (b), 18 (c), 0 (d)**, with six modules carrying no stretch at all, verified rather than assumed. It was declared **the normative enumeration**, above F-47's per-foreign-call table, and it carried its own reopening protocol.

**What it proved, and it did prove something.** Nine real findings across eleven stretches, all fixed in that pass: two were the fifth review's own (C5-01, C5-02) and seven were new — `placeholder.ts`'s class write, and six in `spec.ts`. Their shape is the finding that outlives the table: **every one of them was at a module that already held a reading, and the reading was simply not the last thing before the consequence.** Six of the seven were publications into state teardown had already scrubbed and would never scrub again — a class of defect the module-level quantifier in I-36 (1) could not see _at all_, because the module was provisioned. That is a genuine result and it is why the sweep was worth doing.

**Why it could not be maintained.** Its domain was keyed on consumer-**overridable** members, and that set is chosen by the consumer rather than by the library: it cannot be enumerated, this document said so on I-36's own line, and some of its members are paired so that no reading can be placed between them. A whole-program table over an unbounded domain is complete only until the next composition is written. Four consecutive review passes each closed the one site the previous reviewer happened to reproduce, and the fifth found seven more _inside modules the fourth had certified_ — that is the signature of a domain that does not terminate, not of inattentive reviewers.

**What replaced it.** D-37 replaced the table's **domain**, not its verdicts. Every (a) row's finding is preserved as a defect that was real when it was found; what is withdrawn is the obligation to keep re-deriving rows like it. Under D-36's transaction bracket the (b) verdict becomes universal — teardown no longer runs underneath a stretch, so the boundary undoes frame writes, DOM mutations, dereferences and started animations wherever they occur — and the (c) verdict becomes vacuous, because a conforming residue is only interesting in a domain that would otherwise have counted it. What remains is act (a), invoking a declared consumer slot, which the export table already enumerates. Probe A measured the replacement rather than asserting it: **27 of 33 statement-level readings retire, two more collapse into one pre-publication revalidation, and four survive — all four act (a)**. The 62 rows are not reproduced here; the fifth review's own summary of them, above, is the part worth keeping.

**Two rows are load-bearing elsewhere and are carried forward by name, not by verdict.** The `placement.ts` rows recorded that `applyMechanics` reads `visual.offsetWidth`/`offsetHeight` and then performs six attribute and style writes on the element the placeholder factory returned. That content is now the subject of two Revision 2 decisions rather than of a liveness verdict: the **writes** are what **D-39**'s required `activation.rollback` undoes when the preparation is never adopted, and the **reads** are what **D-43** replaces, because one offset-box window is not the footprint the visual removed — the removed footprint is `boxPre − boxPost`, measured before the lift and again after the visual leaves flow. Losing those two rows would lose the mechanical description both decisions are written against.

**Its reopening protocol goes with it.** A missing or wrong row is no longer a finding, because there is no longer a table to complete. What reopens D-37 instead is narrower and is stated in §[00](00-index.md): a post-close act that is neither a declared-slot invocation, nor an admission, nor a lifecycle or domain publication, **and that the transaction boundary cannot undo**. The sixth-act example the old protocol named — a `scrollIntoView` or a `focus` on a node that outlives the operation — is exactly the shape to watch, and under D-37 it is a question about the _finite domain being wrong_, which is answerable, rather than about the _table being incomplete_, which was not.

## Open before implementation

Ordered by how much each could still move the design. **Q-1, Q-7 and Q-12 are now answered** (see the resolved table above); Q-7's entry is left in place below, marked answered, because two records carried its blocking status forward after the answer landed.

**Q-4. Does the behavior-tag count survive? — the third tag arrived, was investigated, and the boundary held.** Inherited from probe 1's Q-6. The question was posed at two tags — coalesced spatial frame, collection replacement — with a third or fourth stated as a **signal worth investigating**, not proof the boundary is misplaced.

**A third tag exists and has since Checkpoint B**: `TAG_INVALIDATION`, which carries a failure raised from a native scroll/resize listener back into a seam, because a seam is the only place a stage can be classified. The sortable behavior declares `config.actionTags: 3`. This document and 02 both said two until the Phase 14 pass, and the Phase 14 revision initially repeated the stale number as evidence that nothing had grown — corrected in both places.

Investigated, per the question's own terms, the answer is favourable. The third tag is **not** a lifecycle request wearing an action's clothes, which is what Q-4 watches for: it does not ask for admission, activation or release, it asks for a seam it can throw inside. And the pressure that motivated the question — keyboard sorting — did **not** become a tag: D-32 made it a second admission member.

Still open, narrowly: the free-drag probe wants two tags of its own (policy update, controlled position), and whether a _fourth_ on one behavior indicates something is a question a second implemented behavior answers, not this one.

**Q-13. Does a discrete operation ever need to stay `ACTIVE`?** — new with D-32. A command is one slot: the kernel activates and releases it without further input, which is the shipped keyboard's semantics and the ledger's retained behavior (§4). A multi-press mode — pick up, move with several arrows, drop — is not expressible, and deliberately so: it needs a producer of a release that the kernel does not own, which is the lifecycle-request protocol 02 declined to reserve. Phase 16's accessibility review is where the case would come from, and it would reopen the contract rather than be worked around.

**Q-6. Is `RECOVERY_HOME` right for a rejected reorder?** Inherited from probe 1's Q-3, now behavior-owned rather than kernel-owned, which makes it cheaper to change. Returning the visual to its grab origin is what ships, but with a placeholder-based sortable the home slot may have moved under an accepted concurrent update. The test matrix should include a rejection after a collection change.

**Q-7 was here, and is answered.** _How is the layout-displacement feature's element set determined?_ — inherited from probe 1's Q-4, and **answered at Phase 11 by M-4 below**: the set is the **span between the two gaps**, not the destination view (2.3 ms against 0.156 ms at 800 rows), and **no shared read phase** is introduced — the invalidation is the cheap part, and after the span answer there is no duplicate full-list read left. **Narrowed (D-37), and this group loses more than the other.** It was written to pin the _indirect_ clause — the barrier standing in front of a consumer-owned node's own platform members — which is precisely what D-37 withdraws. **Retained**: the entry barrier (a `refresh` entered on an already-closed controller calls the resolver zero times), which is act (a) reached through the release path where `settleDisplacement`'s hooks run immediately before `resolveInsertion`; and the behavior's reading between the `beforeMove` pipeline and `movePlaceholder`, which stops a declared-slot walk. **Retired**: the candidate's own `getBoundingClientRect()` cases including the no-`visual()` composition; the `xy()`-only `compareDocumentPosition` case; both `layoutAnimation()` measurement passes and the `animate()`-destroys case; and the real-composition `lazyY()` + `layoutAnimation()` case with its shifted-rect requirement. All of them assert that an overridable platform member is not reached, and all of them are now bracket-discharged — probe A counted seven displacement tests and five axis tests in exactly this class. **The five axis rows are the published-ceiling withdrawal itself** (§[03](03-feature-composition.md) §`y()`/`xy()` and the README), and are the only failures in the set that required a documented contract change rather than a restatement. The group's closing note — the untested defence-in-depth readings inside `anchorTarget`, `release.effect` and `createPlaceholder` — is discharged the same way: they are removed with the rest, and library execution still completes physically **before the next statement** — the placeholder is removed and the visual restored with no `await` — so the ordinary case is unchanged · `destroy()` called from inside `onStart` leaves the placeholder present when the call returns and gone once the transaction unwinds · the returned `Promise<void>` **settles exactly once**, and repeated `destroy()` calls return the **same promise object**, so two `.then` handlers on two calls each fire once · a consumer throw with **no** destroy leaves the bracket closed, and a later ordinary `destroy()` still tears **Logical versus physical liveness — new (D-38, I-37)** · **a liveness reading must not use `presentation.signal.aborted`**, and the discriminating fixture is the one that produced the only three failures the bracket caused on its own: a destroy raised from the activation survival conjuncts, from the placeholder insertion, and from a reentrant path — under deferral the signal has not yet fired when the logical latch is already set, so a site reading it publishes runtime state and calls `onStart` **after** the close. Assert `onStart` is not called, on the logical latch, and assert it in a fixture where the two readings actually disagree — a test that passes with either reading proves nothing · the same rule as a structural check: no first-party liveness site reads a disposed lifetime, a nulled slot or a detached node to answer _is this alive_ · the two former signal readings collapse to **one** pre-publication revalidation, asserted by placement (nothing is published between the reading and `onStart`) rather than by count · **the sanctioned reading is `KernelHost`'s logical-liveness member** (D-53), and a behavior that maintains its own mirror instead is asserted to agree with it in the case that separates them — a `panic()`-initiated close, where a hand-rolled `rt.closed` mirror set only by `controller.destroy()` reads false and the kernel's member reads true · the member is **readonly**, pinned by `@ts-expect-error` on a write, since a behavior that could set the latch could fake liveness in both directions.

**Placeholder rollback — new (D-39)** · a `placeholder()` factory element whose preparation is discarded comes back with **no library-authored attribute** — no `data-drag-placeholder`, no `aria-hidden`, no copied `slot`, no inline style property — and **no library-authored class** · the element's **own** pre-existing attributes survive with their values, `slot="mine"` included · the same for a **cancelling** factory as for a destroying one: a `cancel()` from inside `placeholder()` invalidates the seam and the element comes back clean · the guarantee is asserted as an **attribute map comparison, not `outerHTML`** — a removed-then-restored attribute is re-appended, so the honest guarantee is same names and same values, not same bytes · `class=""` and `style=""` residues are asserted absent, which requires the normalizing undo to be registered first so LIFO runs it last · the library's own `<div>` records **no** rollback, because dropping it is the undo · a refused acquisition (the factory returned the item, the visual, or a connected node) **releases before it throws** · **the negative control**: every case above fails if `rollback` is removed, which is what pins D-39's mechanism claim — deferral alone does not close this, because the preparation is never adopted.

**Abandoned resolver settlement — new (D-40)** · a post-release `cancel()` with a genuinely pending `onReorder` — a hand-held Promise released after a real gap change, so the round trip is not a proven no-op — produces **exactly one** terminal callback · a later **fulfilment** of the abandoned resolver produces no second terminal and does not revive the operation · a later **rejection** produces **no unhandled rejection**, asserted with a real `unhandledrejection` listener on `window` rather than by inspection · presentation is restored — the placeholder is gone after the cancel · the terminal is `canceled`, and **no `aborted` result exists**: the assertion names the result, since asserting only "one terminal" would pass under either taxonomy · **the `onEnd` union is closed at four arms** — `accepted`, `noop`, `rejected`, `canceled` — asserted as an exhaustive `@ts-expect-error` on a fifth, because a superseded five-arm draft is the failure mode this row guards · **the late-rejection case must be driven after the attempt has lost currency, not merely after it completed**: the abort guard cannot key off `completed` alone, so the fixture settles the abandoned resolver once a _newer_ operation owns the controller, which is the ordering that discriminates a `catch` outliving its attempt from one torn down with it · `destroy()` during a live operation publishes **no** terminal at all, which is I-31's stated exception rather than a missing callback.

**Two-window footprint — new (D-43)** · the removed footprint is `boxPre − boxPost`, measured before the lift and again after the visual leaves flow, and the placeholder is sized from that difference — **not** from `visual.offsetHeight` · the discriminating fixture is the nested one where a sibling remains in the box: `boxPre 62 − boxPost 32 = 30`, the list collapses by exactly 30, and **both** single-window candidates are wrong in different directions (`box` 62, `visual` 60) · the error is asserted **for the whole drag**, not only at landing — the shipped single-window rule runs the list 30 px too tall from activation onward (`180 → 210`) · both windows are **offset-box** reads, pinned by a fixture with a running translate, which corrupts a viewport-rect top by 60 px while leaving height unchanged · `box(item) = visual(item)` by default, and a config supplying only `visual` behaves exactly as before · `item.after(placeholder)` anchoring and the copied `slot` attribute are unchanged, and the slotted fixture is what pins the `slot` copy as required rather than incidental · the stated scope limits are asserted as limits, not repaired: visual order must follow DOM order, rule-placed layouts are unsupported, and grid requires `box === visual`.

**Collection source and invalidation — new (D-44)** · `items()` is called for the **current** committed collection rather than once at construction, and a fixture that changes its return value without calling anything sees the change at the next invalidation · `controller.invalidate()` with the **same array identity** invalidates geometry only — **no** snapshot, **no** reconcile, and **no** O(n) copy, asserted by instrumenting the copy · `invalidate()` with a **new array identity** takes the structural branch: snapshot, reconcile, geometry invalidation, one shallow copy · a warm invalidation storm (resize, zoom) performs **zero** copies, which is the property the identity test buys · every `updateItems()` case in the groups above holds unchanged under `invalidate()`, including the `onStart` FIFO case (F-32) and the invalidating-replacement case (F-28) · after release the proposal is frozen and a structural invalidation does not reinterpret it · **`updateItems` is absent from the public surface**, asserted by the export test, and no `itemCount()`/`itemAt()` protocol replaces it.

**Authored-commit precondition — new (D-42)** · after the authored commit and before the authoritative landing measurement, the library checks **O(1)** that the placeholder is still connected and still a sibling of the item · a supported commit — an append loop, and keyed/morphdom-style movement — passes the check, re-anchors, and lands correctly · `replaceChildren`, an `innerHTML` rebuild and container replacement each **fail** the check, **report through `onError`**, and — per **D-49**, which supersedes this decision's original landing clause — **skip the landing animation and join immediately** rather than landing from the unrepaired position, with **nothing recovered** · the two failure sources, a throwing measurement and a failed precondition, are asserted to reach **one** branch rather than two · the assertion is the report _and_ the absence of a second terminal: pre-D-42 all five strategies reported `onEnd` **once** and `onError` **zero** times, so a test that checks only the terminal passes against unfixed source · the failure signature the check exists to catch is pinned directly — a detached placeholder measures `0×0` at the viewport origin and the row travels `(46,133) → (0,0)` over 12 frames before teleporting back · the check is **not** renderer detection: it is asserted to be two reads, and no commit strategy is inspected or named at runtime · the active-drag cross-container refusal (D-27) is **unchanged**, and the case that would have needed it relaxed is out of contract rather than recovered.

**Input policy — new (D-46, probe E)** · **caret survival on a press that never activates**: a `pointerdown` inside a text input inside a draggable row leaves `defaultPrevented` false, the caret placed where the user pressed, and the selection intact — asserted on a press that crosses **no** activation threshold, which is where six of probe E's eight failures lived · admission **declines** on interactive and editable descendants, and the decline leaves native behavior wholly intact (I-32) · **`event.isComposing === true` never admits**, on either ingress · **arrow keys in a text input do not reorder**: `ArrowRight` inside a nested input moves the caret, leaves `defaultPrevented` false, fires **no** `onStart`, and produces **no** proposal — the pre-D-46 behavior was a complete accepted reorder `{from:2,to:3}` from that single keystroke, so the assertion must cover the caret **and** the absence of the whole operation · `contenteditable` keeps its editing navigation, and native controls keep their own keys · plain-text selection inside a draggable **non-interactive** region is requested with a modifier and is not inferred · click, `href` navigation and ctrl-click are unaffected, which is the non-regression condition for only `pointerdown` ever having been prevented · **`handle()` is not the accessibility answer**: a fixture composing `handle()` resolves the interactive-descendant cases but loses keyboard reordering unless the grip is focusable, and that obligation is asserted rather than assumed.

**Terminal totality — new (D-66)** · **every started operation** on a live controller publishes exactly one `onEnd`, asserted across the whole failure-stage set rather than on a sampled stage — this is the assertion that would have caught the skip, and it is cheap because the stage list is closed · a consequential failure **before** any domain result exists publishes `{ type: 'canceled' }` whose `reason` **is** the classifying error, by identity · a consequential failure **after** the authored commit publishes `{ type: 'accepted' }` **and** one `onError` — the existing-result-wins branch, and the case D-66 was decided on · `onError` precedes `onEnd` in both, and `FAILURE_TERMINAL_CALLBACK` is the one stage where it follows · `destroy()` after `onStart` still publishes **no** terminal (I-31's only surviving exception).

**Terminal boundary — new (D-66, Q-15)**, and these are the rows that stop the guarantee being widened by accident · a throw in `activation.prepare` publishes **one `onError` and no `onEnd`**, because `onStart` never ran · a throw in `activation.effect` **before** the `onStart` call does the same · a throw in `activation.effect` **after** the `onStart` call publishes `onError` **and** one `onEnd({ type: 'canceled' })` — the pair is the assertion, since either alone passes under a wrong marker placement · **`onStart` itself throws → `onError` and one `onEnd({ type: 'canceled' })`**, which is the row that fails if the marker is advanced _after_ the call instead of before it: the consumer has been told the drag began and is owed an end · a throw from `admit` publishes neither, and reaches `reportFailure` with no operation (Q-1).

**Cancellation stage of the fallback — new (D-66)** · a failure classified **after** `onStart` and **before** the round-trip opens carries `AT_PROPOSAL` · a failure classified while `onReorder` is in flight carries `AT_CONSUMER` · **a throw in `release.effect` carries `AT_PROPOSAL`** — the regression test for the rejected `proposal !== null` derivation, which would report `AT_CONSUMER` here because the proposal is already committed while the staged command was never executed.

**Contextual landing duration — new (D-67)** · `duration({ distance, from, to })` is invoked **once** per landing, at settlement, with `distance` equal to the straight-line magnitude between `from` and `to` · an out-of-domain or thrown result classifies at that moment, exactly as the fixed form's construction-time check does at construction · `duration: () => number` is **not** a compile error and must not be tested as one (F-52) — a zero-parameter function is assignable to any signature, so a shipped thunk keeps compiling, keeps returning the right number, and silently ignores the argument. **Assert the behaviour instead**: a zero-argument function is still invoked once per landing and its result still validated. The migration is source-compatible, which is the honest claim · the reduced-motion collapse still happens **after** resolution and validation, so a bad result is diagnosed under `prefers-reduced-motion: reduce` exactly as it is without.

**Middle-tier authoring — new (D-61)** · a third-party installer written against `@ydinjs/drag/sortable/feature` alone — importing no other subpath — compiles, installs, contributes an `insertion` capability, and is retired in reverse installation order · the installer it produces is assignable to `SortableConfig['axis']` declared in `sortable.js`, which is the one-identity clause surviving from the retracted clause 3 · a fixture that imports **only** `sortable.js` still cannot construct one, and the `@ts-expect-error` proving it is the boundary's only remaining enforcement.

**Terminal channel — new (D-62)** · every settlement arm reaches `onEnd` exactly once and `onFinish`/`onCancel` do not exist on the surface · the argument is assignable to `ReorderTransactionResult` and an exhaustive `switch` over its four `type` values compiles with no `default` arm — the consumer-side half of what F-37 used to test in the library.

**Landing surface — new (D-63)** · `landing({ run })` is a **compile error** at the ordinary tier and `LandingStart` is not exported from `sortable/landing.js` · a kernel-tier behavior still installs a custom runner and reaches `done()`, `fail()` and `destroy()` unchanged, which is what makes this a tier move rather than a deletion · `landing({ duration: () => n })` still resolves at settlement (L-6 parity, and see 03 §Public option domains for what review 3 §10 additionally proposed).

**Error surface — new (D-64)** · `onError` receives a `DraggableError` whose `code` is one of the four fault classes, and `FailureStage` is not reachable from `sortable.js` · the stage → code mapping is **total**: a test that enumerates every `FAILURE_*` constant and asserts a code for each fails when a stage is added without one — this is the assertion that stops the `default:` arm D-60's history warns about · probe C1's regression asserts `onEnd` once **and** one `DraggableError`, never mutual exclusivity.

**Placeholder slot — new (D-65)** · `placeholder(context)` returns a fresh detached element and the library adopts it; `createPlaceholder` and `placeholderClassName` are not config keys · the default element still carries `data-drag-placeholder`, which is the branding route that replaces `placeholderClassName` and therefore needs a test of its own now that it is load-bearing.

**Probe scenarios that become acceptance tests.** Probes **A**, **C1** and **E** should survive into the production suite rather than being discarded with their spikes — they are the executable evidence the freeze rule required for D-36…D-39, D-42, D-43 and D-46, and each one already discriminates against unfixed source, which is the property this matrix asks of every new row. The owner has stated that remaining probe scenarios may become implementation acceptance tests unless reconciling the contracts exposes a new architectural contradiction. Two carry-over conditions from probe A are worth naming here because they are easy to lose in a port: its cases are **Chromium only**, so a second engine is owed; and the bracket's cost — one increment, one decrement and one branch per drain — is **unmeasured**, as is the effect of removing 27 predicate calls from the hot path, so neither belongs in the contract as a performance claim until it is.
