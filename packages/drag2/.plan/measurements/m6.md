# M-6 — the write census

**Status: run 2026-08-20. P-01 opens.** The pointer arm exceeds one `lift.write` per rendering opportunity on a stream the browser itself demonstrably coalesced, so the saving a write gate would make is real and is not zero. **D-96's suspended within-frame half closes with it**: `constrain.apply` exceeds one per tick on the same arm, so collapsing several resolves inside one frame is not bounded at zero either.

**No gate is implemented in this handoff.** Phase 22 designs it, including the flush obligation on every terminal path, and only then is the cost of one write worth measuring.

M-6 is the sixth Phase 21 measurement, added by **D-97** after M-1′ raised P-01 rather than answering it with a proxy. It is taken against [`phase-21.md`](phase-21.md) §M-6, whose decision rule was fixed before the run.

## What is counted, and why the denominator is an rAF tick

Two counters, read at every `requestAnimationFrame` tick: **`lift.write` calls** and **`constrain.apply` calls**. **This is a count experiment and not a timing benchmark** — no duration appears in it, and the cost of one write is deliberately not measured, because the count is what decides and a cost taken first would be the convenient number M-1′ refused.

A write gate would itself be built on rAF, so counting per rAF tick counts exactly what such a gate would collapse, and the figure is refresh-rate independent by construction.

**`lift.write` is counted at the assignment it performs.** `write()` is exactly one `visual.style.transform = compose(x, y)` (`kernel/presentation.ts`), so an accessor over that one property of that one element counts the calls and nothing else; it forwards to `setProperty`, and a structural row reads the committed transform back to prove the element still moves.

**Counting `onMove` instead would have been wrong rather than merely indirect.** The `TAG_POSITION` effect renders through `lift.write` and does **not** call `onMove` (`free-drag/spec.ts` §Behavior actions), so an `onMove` counter would have reported **zero** for the entire `moveTo()` arm — the half of the census that has to move.

## The validity control, and the run that fails it

Every dispatched `pointermove` records `event.getCoalescedEvents().length`. **A length above one is the only evidence that the injected stream genuinely outran presentation**; without it a slow injector returns _one write per frame_ and it reads exactly like a bound.

The census is driven at three injector paces. `wave = 1` is Playwright awaiting each dispatch before sending the next — the driver's natural pacing. Above one, a small wave is issued without waiting for each acknowledgement: still every event through `Input.dispatchMouseEvent`, still the browser deciding what to coalesce, but no longer rate-limited by the round trip.

| wave | achieved rate | dispatches | coalesced > 1 | max coalesced | **verdict** |
| --- | --- | --- | --- | --- | --- |
| **1 — sequential** | ~59 /s | 240 | **0** | 1 | **INCONCLUSIVE** |
| **2** | ~129 /s | 211 – 213 | **27 – 29** | 2 | **VALID** |
| **4** | ~309 /s | 121 – 124 | **64 – 72** | 3 – 4 | **VALID** |

**The `wave = 1` arm is reported and its counts are not used.** It is the run the control exists to catch: Playwright's sequential mouse path emits about 59 movements per second on this machine, which is _below_ the display rate, so nothing it returns can bound writes per frame in either direction. **Its `p95 = 1` is not evidence for one write per frame**, and is not quoted as such anywhere.

**That the control can fail is itself the demonstration that it discriminates.** The same file, the same counters and the same assertions produce INCONCLUSIVE at one pace and VALID at the next, so the VALID verdict is a measurement rather than a formality.

## Arm 1 — platform pointer traffic

Writes per rAF tick, three runs:

| wave | ticks | **writes p95** | **writes max** | mean | applies p95 | applies max |
| --- | --- | --- | --- | --- | --- | --- |
| 1 — _inconclusive, not evidence_ | 242 – 243 | _1_ | _6_ | _1.01_ | _1_ | _5_ |
| **2 — valid** | 96 | **3** | **7** | 2.25 – 2.27 | **3** | 6 |
| **4 — valid** | 24 | **8 – 9** | **8 – 10** | 5.25 – 5.38 | **8** | 8 – 10 |

**The decision rule opens P-01.** Its opening condition is the pointer arm's `p95 > 1`, and on the valid arms p95 is **3** and **8**. The saving is `(writes per tick − 1) × one write`, which at the wave-2 pace is two writes in twenty of every hundred frames and more in the tail.

**What this establishes about the platform, stated carefully.** Chromium coalesced a substantial fraction of the stream — a quarter to a half of dispatches carried more than one movement — **and still delivered several separate `pointermove` dispatches inside one rendering opportunity**. Coalescing is a mitigation, not a one-dispatch-per-frame guarantee, which is exactly what D-97 said could not be assumed and what D-96 had promoted to structure.

**The lower-denominator caveat is on the record**: the wave-4 arm has only 24 ticks because the flood finishes quickly, so the wave-2 arm at 96 ticks is the primary evidence and wave 4 corroborates the direction rather than establishing it.

**One observation that is deliberately not evidence.** The `wave = 1` arm shows a `max` of **6** writes in a single tick despite its control failing — a stalled frame draining a backlog. It is consistent with the valid arms and it is recorded, but the control governs: no count from that arm is used.

### What closes with it

**D-96's within-frame suspension closes.** `constrain.apply` reaches **p95 = 3** and **8** on the same valid arms, so more than one resolve per frame does occur and the only ground given against collapsing them — that fewer than two `apply` calls happen per frame — does not hold. **Collapsing resolves inside one frame is no longer refused.** Holding a rect **across** frames stays withdrawn on its own independent ground: it serves the previous frame's rect to this frame's clamp and moves the visual, and no count licenses that.

## Arm 2 — consumer `moveTo()` traffic

**Kept analytically separate from arm 1**, because this is not the platform's rate; it is the consumer's. `moveTo()` dispatches `TAG_POSITION` synchronously, its effect renders through `lift.write`, and it is unbounded per frame by design (D-71).

| shape | ticks | writes p95 | writes max | mean |
| --- | --- | --- | --- | --- |
| **driven from the consumer's own rAF** | 91 | **1** | 5 | 1.04 |
| same-frame burst of 2 | 31 | 2 | 5 | 2.10 |
| same-frame burst of 8 | 31 | 8 | 8 | 7.90 |
| same-frame burst of 32 | 31 | 32 | 32 | 31.13 |

**A consumer calling `moveTo()` once per rendering opportunity produces one write per tick.** A consumer calling it `n` times inside one frame produces exactly `n` — the census tracks it 1:1 at 2, 8 and 32, which is also the sharpest available check that the counter is not saturating.

**This surplus is documented, not gated.** It is created entirely by a rate the consumer chose, and a library does not gate away a rate its consumer deliberately chose. It is recorded here as a consequence of the `moveTo()` contract: calls above the display rate cost one full render each, and the API does not coalesce them. **Nothing in arm 2 contributes to P-01's verdict**, which rests on arm 1 alone.

## The falsification

**Constructed before any result was recorded**, because a counter permanently stuck at one would pass every arm of this census and read as a bound. Eight `moveTo()` calls inside a single rAF callback must produce more than one write in one tick, by construction — and the assertion runs on **every suite run**, not behind the measurement flag.

It holds. The three burst rows above are the same property at three magnitudes, and the rAF-driven row is its complement: the same instrument returns **1** when the traffic really is one per frame, so it is not merely biased high.

Two further structural rows pin the instrument to the system it claims to measure: the counted element still renders a real transform, and the constraint's `ConstraintView.visual` is the same node whose `transform` the write counter shadows.

## Engine scope

**Chromium only, and that is sufficient for this verdict.** D-97's scope clause makes one supported configuration exceeding one write per tick enough to **open** the question — it is a close that would have needed the engine named. No second engine was run.

**What would reopen the close that did not happen**: nothing, since P-01 opened. **What would change the size of the saving**: a user agent that coalesces strictly to one dispatch per frame, which would reduce arm 1's surplus without eliminating arm 2's.

## What M-6 changes

- **P-01 opens.** The per-sample visual render does repeat within a rendering opportunity under input the browser itself treats as faster than the frame. Phase 22 designs the gate **including the flush obligation on every terminal path** — a deferred write that never runs leaves the visual behind the operation — and weighs that contract cost. **No gate is implemented here.**
- **D-96's within-frame coalescing suspension closes**; the across-frames withdrawal stands untouched on its own ground.
- **The `moveTo()` surplus is classified as consumer-created** and recorded as a documented consequence rather than a gating requirement.
- **The repo gains Playwright input commands** for the drag2 browser project, which is what made a valid pointer arm possible at all.
