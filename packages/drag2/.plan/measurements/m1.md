M-1 ([05](../contract/05-lifecycle-invariants.md) §Measurements owed) asks whether the generic frame copy on the pointer path costs anything a specialized publication would save, and what one pointer sample actually costs.

## Harness

[`packages/drag2/tests/perf/m1.browser.test.ts`](../../tests/perf/m1.browser.test.ts), checked in. Structural assertions — including the equivalence check — run in CI on every suite run; the timings are opt-in with `VITE_DRAG_MEASURE=1` and assert nothing.

- **Engine.** Chromium (Chrome for Testing 150) via `@vitest/browser-playwright`, headless, on the devcontainer CPU. Absolute numbers are machine-specific; every conclusion rests on a ratio or on an order of magnitude.
- **Policy.** 5 discarded warm-up iterations; a calibrated batch (doubling until a sample clears 2ms, because `performance.now()` is clamped to 100µs); 21 samples; **median**, since a mean is dominated by its first iteration and by GC.
- **Variants.** `generic` is what ships — `beginFrame` (an `Object.assign` over the whole frame), two field writes, swap. `specialized` writes the two pointer fields into the committed frame: no copy, no swap.
- **Equivalence.** 64 samples through both variants must leave byte-identical committed frames, asserted before any timing is quoted. A second assertion pins the _bound_: the specialization is only valid for a sample that changes nothing else, so it could be a second path, never the only one.
- **Frame shapes.** Behavior part sizes 3, 8, 12, 16, 20 and 28, plus a polymorphic scenario that drives three shapes through one call site — the concern F-24 actually raises.

**Run one measurement file at a time.** The browser project runs test files in parallel, and two measurement suites sharing a page inflate every absolute figure by roughly 2× (the shipped-shape copy reads 0.214 µs instead of 0.098 µs). Ratios and the cliff location survive it; absolutes do not. Every number quoted here comes from a run of this file alone:

```
VITE_DRAG_MEASURE=1 npx vitest run -c vitest.config.ts \
  --project browser tests/perf/m1.browser.test.ts
```

The shipped frame is **8 part fields** (`SortableFramePart`) on top of 7 kernel fields: the "15-field `Object.assign`" the plan names.

## Answer 1 — the copy stays, and now there is a number

At the shipped shape the copy is **0.098 µs of a 2.64 µs sample: 3.7%**. The sample itself is **0.017% of a 16 ms frame**. Removing the copy would buy ~0.09 µs per sample while splitting frame publication into two paths — one transactional, one not — and the second path is only legal for samples that change nothing but the pointer, which the kernel would have to prove at every call site.

So F-24's _"removing the copy would be performance theatre"_ is **correct**, and it now says so with a number instead of a conviction.

## Answer 2 — but the claim is bounded, and the bound was not known

The copy's cost is **not linear in frame size**. It is flat and cheap to ~12 part fields and then jumps **10×** between 12 and 16 — 0.147 µs to 1.465 µs — after which it grows slowly again. That is an engine cliff (V8's fast path for `Object.assign` over objects with few enough in-object properties), not a property of the contract, but the contract lives on the cheap side of it by 4 fields.

**This is the part F-24 could not have known by inspection.** A behavior with a larger frame part — or a second behavior sharing the kernel — crosses it, and the copy goes from 3.7% of a sample to roughly 55%. The claim is therefore recorded as _the copy is free at this frame size_, with the size named.

The polymorphic case costs 0.586 µs — 6× the monomorphic 8-field figure, and between the two sides of the cliff, as expected when one call site sees three shapes. It is still 22% of a sample. Several controllers of _different behaviors_ on one page pay this; several controllers of the _same_ behavior do not, because the shape is the same.

## Answer 3 — I-26

I-26 claims one pointer sample "creates no wrapper, tuple, collection or protocol object". 20,000 samples produced no measurable net heap growth, which **bounds retention at zero and transient allocation below the noise floor of a precise-memory reading**.

It is not the same statement as the invariant. "Creates no object" is about allocation, and a collector that keeps up makes allocation invisible to a heap reading. The stronger form stays what 06 says it is — a claim established by inspection — and this is the executable evidence that nothing contradicts it.

## What would reopen this

- A behavior part above ~12 fields, or a second behavior whose part pushes the shared call site over the cliff.
- A frame that stops being flat scalars: the copy is shallow, so its cost is the field count, not the data.
- An engine whose `Object.assign` has a different cliff, or none. The 12-to-16 boundary is Chromium's and is not a portable constant.

## Re-measurement — D-35's two scalar writes (K-6, 2026-08-15)

`VisualLiftSession.write` now records the delta it composed, so every rendering sample carries **two scalar field writes** it did not carry before (D-35). K-6 owes a re-measurement for them, under the same reproducibility standard as the original: same harness, same engine class, same policy, both arms measured in the same session.

**Method.** The tree at HEAD and the tree with the kernel step, alternated on the same machine in the same minute, three runs each, `VITE_DRAG_MEASURE=1` and this file alone (parallel measurement files inflate every absolute). Nothing else changed on the move path.

|                            | before                | after                 |
| -------------------------- | --------------------- | --------------------- |
| end to end, 50 rows        | 3.71 / 3.32 / 3.32 µs | 3.22 / 3.52 / 3.32 µs |
| end to end, 200 rows       | 3.52 / 3.42 / 3.42 µs | 3.52 / 3.52 / 3.81 µs |
| allocation, 20 000 samples | 0 B per sample        | 0 B per sample        |

**This is a null result, and it is stated as one.** Every figure above is a multiple of ~0.098 µs — `performance.now()`'s clamp divided by the calibrated batch — so one tick is the smallest difference this harness can express. The two arms' ranges overlap, and the medians move in opposite directions between the two row counts. **There is no resolvable regression at ~0.1 µs per sample**, and that is the whole of what was measured.

**It is deliberately not written as an upper bound.** Three runs per arm at one-tick granularity cannot establish _the cost is under 0.1 µs_; they establish that any cost is smaller than the run-to-run spread, which is itself about one tick here. A real bound needs what this run did not do — enough samples to put a confidence interval on the difference, or a micro-benchmark that isolates `write` from the rest of the sample — and neither is worth building for a change whose own accounting predicts something unresolvable: two field writes into an object the line above just wrote through. If a bound is ever needed, that is the work it takes.

The sample itself remains ~0.02% of a 16 ms frame on both arms.

**Allocation is the half that did not come back null**, and it is the one that could have gone wrong. The recorded delta is one object per operation, written in place; re-publishing `{ x, y }` per sample would have put an allocation on the path I-26 claims creates no object per sample and F-24 spent a measurement keeping clean. 20 000 consecutive samples still produce no measurable net heap growth.

**The absolutes have drifted since 2026-08-02** — 3.3 µs where the original run read 2.64 µs — on a devcontainer whose CPU is shared. That is why both arms were run in one session and why the conclusion rests on the paired comparison rather than on either column against the older table. The frame-copy arm read 0.104 µs at the shipped 8-field shape after the change, with the 12-to-16 cliff in the same place — quoted for continuity rather than as a comparison, since that arm drives the harness's own publication variants and never reaches the lift.

**What this does not re-open.** The frame is untouched, so M-1's answer 1 and its cliff bound stand exactly as written.
