# M-4 / Q-7 — the displacement element set, and the duplicate layout read

**Status: answered. Blocking gate for `layoutAnimation()` — cleared. Accepted as M-4 at the phase 11 sign-off, 2026-08-02.**

Q-7 ([05](../contract/05-lifecycle-invariants.md) §Open questions) asks two things that turn out to have one answer:

1. does the displacement set contain every item in the destination view, or only those between the old and the new gap?
2. can the axis feature's index rebuild and `layoutAnimation()`'s before/after measurements share **one** layout read around the committed placeholder move?

> **Naming and timing, corrected 2026-08-08 (C4-03).** This write-up was authored at Phase 11, when the axis rule was one feature called `vertical()` and it rebuilt its index **lazily, on the next spatial frame**. Both have since changed and the conclusions did not: Phase 17 split the rule into the sibling features `y()` and `xy()` over a shared `RectIndex`, and Phase 11's own answer 1 is what made the rebuild **eager** — the behavior now calls it inside the committed-move bracket (`src/sortable/spec.ts`, `action.effect(TAG_SPATIAL)`), in the one window where no displacement offset is applied. The measurements below are unchanged and were not re-run; where the text says `vertical()`, read "the installed axis feature", and where it argues from lazy rebuild timing, see the note in answer 2.

## Harness

[`packages/drag2/tests/perf/q7.browser.test.ts`](../../tests/perf/q7.browser.test.ts), checked in and run in CI. It is a measurement that also asserts: the printed figures are the record, and the assertions are coarse relationships that hold on any engine, so it cannot become a timing flake.

- **Workload.** A real list of `n` 40px rows in a `overflow: auto` container, one placeholder moved one slot per iteration, so every iteration begins with a genuinely dirty layout. `n ∈ {50, 200, 800}`.
- **Policy.** 5 discarded warm-up iterations; then a calibrated batch (doubling until a sample exceeds 2ms, because `performance.now()` is clamped to 100µs and the first version of this harness reported zeroes for every small-`n` shape); 21 samples; **median** reported, since a mean over a forced-layout workload is dominated by its first iteration and by GC.
- **Engine.** Chromium via `@vitest/browser-playwright`, headless, on the devcontainer's CPU. Absolute numbers are machine-specific; every conclusion below rests on a _ratio_.

Four shapes per size:

| Shape | What it is |
| --- | --- |
| `one` | move, then one full read pass — the floor for anything needing post-move geometry |
| `two` | move, then two full read passes with nothing written between |
| `write-between` | move, read all, write a transform to every row, read all again — the real FLIP shape over the whole destination view |
| `span` | move, then read only the two rows a single-slot move touches |

## Numbers

| n   | `one`    | `two`    | `write-between` | `span`   |
| --- | -------- | -------- | --------------- | -------- |
| 50  | 0.053 ms | 0.091 ms | 0.162 ms        | 0.020 ms |
| 200 | 0.194 ms | 0.338 ms | 0.575 ms        | 0.052 ms |
| 800 | 0.675 ms | 1.200 ms | 2.300 ms        | 0.156 ms |

Derived, at n = 800:

- a second full pass over a clean tree costs **0.53 ms**, ~78% of the first. The forced layout is therefore only ~0.15 ms of the 0.675 ms; **the read loop dominates, not the invalidation**.
- `span` ≈ 0.156 ms ≈ the forced layout alone. Reading 800 rects adds ~0.52 ms; reading the two that moved adds nothing measurable.
- full-list FLIP around one move costs **2.3 ms** — 14× the minimal span, and ~7 committed moves would exhaust a 16 ms frame on their own.

## The collection-mutation case

05 asks M-4 for "representative collection-mutation and layout cases, not a static list". The mutation half is discharged **structurally rather than by a timing shape**, and answer 1 explains why: the bracket runs inside one `action.effect` and the queue is run-to-completion, so a collection replacement cannot interleave between `beforeMove` and `afterMove`. There is no cross-version displacement set to measure because none can exist. What the behaviour does when a replacement lands _between_ moves is asserted in `packages/drag2/tests/sortable/displacement.browser.test.ts` — _should stop displacing a row that left the collection_ and _should cancel a displacement it could not track_.

## Answer 1 — the set is the span between the two gaps

Not the destination view. Two independent reasons, and the second is the one that matters:

- **Semantics.** Items outside `[old gap, new gap)` do not change position. A full-list FLIP animates a zero delta for them: work with no visual product.
- **Cost.** 2.3 ms against 0.156 ms per committed move at 800 rows.

The "correct set under a concurrent collection replacement" that Q-7 flags as non-obvious **dissolves structurally**. The bracket (`beforeMove` → write → `afterMove`) runs inside one `action.effect`, and the queue is run-to-completion: a collection replacement is a _different_ action and cannot interleave between the two hooks. The set is therefore always computed within one snapshot version, and the next move recomputes it against whatever snapshot is then current. No cross-version reconciliation is needed, and none is implemented.

**This required a contract change, which is why the gate sat here.** `DisplacementView` carried `{ realm, snapshot, placeholder }` — from which a feature cannot know which elements a move will affect _before_ the write, so it would have to measure the whole list twice to find out. The view now also carries `insertion`, the destination gap, written to the shared per-operation view immediately before the bracket. That is one property write per **committed** move, no allocation, and it is what turns an O(list) bracket into an O(distance) one. `SortableContribution` itself is unchanged.

## Answer 2 — no shared read phase, and none is needed

The measurement was framed around "the forced layout is the expensive part, so paying it twice is the problem". **That framing is wrong**: `two` is 78% of `one`, so the layout invalidation is the cheap part and the per-element reads are the expense. A shared read phase would therefore have to share the _reads_, not merely the invalidation — a much more invasive capability.

It is also unnecessary, for two independent reasons:

- **After answer 1, there is no duplicate full-list read left.** `layoutAnimation()` reads the span (2 rows); `vertical()` rebuilds the list. Sharing 0.156 ms into 0.675 ms buys nothing worth a shared-capability seam.
- **They do not happen at the same moment anyway.** At the time of measurement the axis feature was invalidated by the committed move but rebuilt lazily, on the _next_ spatial frame — one rAF later, after the pointer had moved again. A shared pass would have to change _when_ the axis feature measures, trading a stale-geometry risk for a saving that answer 1 already removed.

  **This is the one argument the implementation overtook, and it strengthens the conclusion rather than weakening it** (C4-03). The rebuild is now **eager**: the behavior calls `measureInsertion` inside the committed-move bracket, after `beforeMove` has released every displacement offset and before `afterMove` replays them, precisely because a lazy rebuild lands mid-animation and measures rows where they no longer are. So the two features' reads *do* now sit in the same bracket — and still share nothing, because they read different things: the axis reads every candidate's **visual**, the displacement reads the **span's rows**. There is no common result to hand over, only an ordering, and the ordering is the behavior's and always was. Re-timing was not an extra read either: a committed move always dirties the cache and the next spatial frame would have rebuilt it anyway.

So: no behavior-owned read phase, no shared geometry-read capability. The two features keep their private caches, which is what H-4 wanted for ownership reasons and what the numbers now also make the cheaper option.

## What would reopen this

- A displacement feature that genuinely needs whole-list geometry (a masonry or grid relayout, where a single-slot move reflows everything). The span assumption is axis-list-shaped, and it is stated as such.
- A list where a single committed move crosses many slots — a fast flick can jump a large distance. The span is O(distance), so the worst case degrades toward the full-list number. It is bounded by what the pointer actually crossed, which is the right bound, but it is not O(1).
