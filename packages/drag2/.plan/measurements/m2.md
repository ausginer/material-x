# M-2 — controller cost, and the frame-task policy

**Status: answered, 2026-08-02. F-4's claim survives with a named crossover; eager-retained stays, and the reason is not the one that was assumed.**

M-2 ([05](../contract/05-lifecycle-invariants.md) §Measurements owed) asks two things: what the closure-per-controller model costs against an opaque state record driven by one static spec, and which of **three** frame-task policies to keep. 05 warns explicitly that a binary eager-vs-per-operation benchmark could select a dominated policy, so lazy-retained is measured as a peer.

## Harness

[`packages/drag2/tests/perf/m2.browser.test.ts`](../../tests/perf/m2.browser.test.ts), checked in. Structural assertions run always; heap and timing figures are opt-in with `VITE_DRAG_MEASURE=1`.

- **Engine.** Chromium (Chrome for Testing 150), headless, devcontainer CPU.
- **Heap policy.** `gc()` before every reading and `--enable-precise-memory-info` — without the latter Chrome quantizes `usedJSHeapSize` to 100 kB and every figure here would be a rounding artifact. Both flags are set for the drag browser project only. Each figure is the **minimum of 5 runs after 3 warm-ups**, because heap noise is one-sided: other allocation can only inflate a reading.
- **Retention.** The graph under measurement is held by a module-level sink, cleared _before_ the baseline is taken. The first version of this harness let each run overwrite the previous graph, so every run freed one while allocating the next and every figure was ≈ 0 — which reads exactly like "costs nothing".
- **The construction models are models.** Rewriting the kernel in opaque-`S` style to measure it is the change the measurement exists to justify. Both stand-ins carry the same 15-field state and the same dozen handlers; only the construction differs.
- **The policies are the real `createFrameTask`.** Only the ownership around it differs.

**Run one measurement file at a time**, for the reason m1.md gives: parallel test files share a page and inflate every absolute figure. Heap figures are the more robust half — they are minima and survive a noisy neighbour — but the timings do not.

## Numbers

**Construction model**, per controller:

| controllers | closure model         | static spec + state   | ratio |
| ----------- | --------------------- | --------------------- | ----- |
| 100         | 49.8 kB (509 B each)  | 13.8 kB (142 B each)  | 3.60  |
| 1000        | 493.7 kB (506 B each) | 137.9 kB (141 B each) | 3.58  |

One `move` call: **closure 0.0013 µs, static 0.0038–0.0065 µs** across runs — a 2.9–5× ratio whose lower bound is the one quoted below.

**Frame-task policy**, 1000 controllers:

| policy | cold | after activation | first drag | `schedule` | retained after 1000 drags |
| --- | --- | --- | --- | --- | --- |
| eager-retained (ships) | 274.6 kB (281 B) | 274.6 kB (281 B) | 0.281 µs | 0.0034 µs | ≈ 0 |
| lazy-retained | 130.0 kB (133 B) | 301.9 kB (309 B) | 0.220 µs | 0.0072 µs | 0.3 kB |
| per-operation | 130.0 kB (133 B) | 301.9 kB (309 B) | 0.269 µs | 0.0076 µs | 0.1 kB |

## Answer 1 — keep the closures, and F-4 was right for the wrong reason

The closure model costs **3.6× the heap per controller — 365 B more, stable across two orders of magnitude of controller count**. At a realistic page (tens of sortable lists) that is under 20 kB. At 1000 controllers it is 356 kB, which is real but is also a page with 1000 drag controllers.

F-4 said the difference was _"expected to be irrelevant"_. It is, at realistic counts. But the reasoning it implied — that closures are a cost to be tolerated for the ergonomics — is backwards on the axis that runs every frame: **the closure call is 2.5× faster than the static-spec call** (0.0015 µs vs 0.0038 µs), because a captured closure is a direct call while the spec form is a property load plus an indirect call with an extra argument.

So the trade is not "pay heap for ergonomics". It is **pay heap for speed on the hot path**, and the hot path is the one the contract cares about (I-26). The closure model is kept, and F-4's sentence is replaced with both numbers.

## Answer 2 — eager-retained stays; the differences are ~150 B and ~4 ns

The three policies are within a rounding error of each other on everything that was supposed to separate them:

- **Cold controllers.** Eager pays 148 B more per controller that never drags — the retained `FrameTask` closure. At 1000 never-dragged controllers that is 148 kB. This is the only figure where lazy-retained wins, and it is the case 05 flagged.
- **Active controllers.** Eager is _cheaper_ (281 B vs 309 B): lazy and per-operation need a mutable slot and the branch that reads it, which costs more than the task it defers.
- **First-drag latency.** 0.22–0.28 µs across all three, inside the noise.
- **`schedule`.** Eager 0.0034 µs against 0.0072 µs — a 2× ratio on a 4 ns absolute, entirely the null-check and the indirection through the slot. It runs once per committed pointer sample.
- **Leaks.** None. A thousand activate/schedule/retire cycles retain nothing under any policy, which is the property that actually mattered.

**Decision: keep eager-retained.** It has the simplest lifetime (created once, cancelled twice), the cheapest `schedule`, no nullable field and no initialization branch — and its cost is 148 B for a controller that never drags. Lazy-retained is the right answer only for a page holding thousands of cold controllers, and 05's warning is discharged rather than ignored: lazy-retained was measured as a peer and lost on active heap, not by omission.

The comment in `SortableRuntime` calling this "an open measurement, not a settled question" is now settled and is updated in place.

## What would reopen this

- A page holding thousands of sortable controllers that are mostly never dragged — the one shape where 148 B × N is worth a nullable field.
- A frame task that stops being one closure over two locals. The 148 B is the task's own retention; a heavier task moves the crossover down sharply.
- A behavior needing more than one frame task per controller, which changes the cold cost without changing the active one.
