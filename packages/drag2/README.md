# `@ydinjs/drag2`

Implementation of the frozen `drag2` construction model: a private kernel executor, a private behavior runtime, and construction-time feature composition.

- **Contract (source of truth):** [`.plan/contract/`](.plan/contract/), documents 00–06, read with the precedence stated in `00-index.md`.
- **Implementation plan:** [`.plan/plan.md`](.plan/plan.md).

The shipped `@ydinjs/drag` is untouched while this package is built. Merging the two is the last phase of the plan and a separate decision, so this package is `private` until then.

## Status

**Phases 0–17 complete: the sortable behavior, whole.** Pointer **and** keyboard input, one-dimensional **and** two-dimensional insertion, the full optional feature set, and the authored-presentation protocol the Phase 14 contract revision replaced — which **Revision 2 then deleted outright**, so that last item is now shipped code awaiting removal rather than a capability. What is still missing against `@ydinjs/drag` is **free dragging**, which is a second behavior rather than a sortable capability — and with one behavior written, every measurement below is still a single-behavior number. The roadmap from slice to package is [`plan.md`](.plan/plan.md) Part II.

**Phases 3–5 are the frozen SPI** and **phase 9 froze the public surface**: any change to a seam signature, or any addition to the export table below, requires the failing-executable-case justification from contract 00. The three known pressure points against that freeze — discrete (keyboard) input, the authored-presentation protocol, and whether a second behavior fits the seam set — were probed in Phase 13 and resolved in **one** contract revision (Phase 14, D-32…D-35), which is re-frozen. Two of the four are implemented; D-34 and D-35 land with the second behavior.

**Revised a second time — Revision 2, the API redesign, D-36…D-60.** Three API review rounds and five probes (A, C1, E, api-1, api-2) produced a redesign of the **consumer-facing** surface, owned by [`.plan/reviews/api-reviews/api-review-final-summary.md`](.plan/reviews/api-reviews/api-review-final-summary.md) and recorded in contract 00 §Revision 2. Phase 14 was four places the SPI could not express something; this is the surface that sits on top of it. In short: `destroy()` becomes immediate-and-terminal with **deferred** physical teardown and a `Promise<void>` return (D-36); the whole-program post-close ceilings are **withdrawn** for a finite declared-slot rule (D-37, D-38); the authored-presentation readiness protocol is **deleted** in favour of the consumer awaiting its own commit inside `onReorder` (D-41); `updateItems()` becomes `items()` + `controller.invalidate()` (D-44); the opaque feature brand is **withdrawn** for plain partial config objects (D-45); the placeholder footprint takes two measurement windows (D-43); `preventDefault()` moves from admission to the activation threshold and the drag suppresses its trailing `click` (D-46, D-54); the box element arrives through admission in the kernel's own vocabulary rather than through a behavior-authored draft field (D-59); a landing that cannot be measured is **skipped rather than faked** (D-49); the four fragment factories that install nothing become plain config keys (D-56); and `sortable()` takes the root and returns its controller directly, with `draggable()` moving to a new `@ydinjs/drag/kernel` subpath while `drag.js` keeps its shared-vocabulary job (D-48).

**`src/` implements neither revision in full, and this section must not be read as a changelog of shipped code.** Of Phase 14, D-32 and D-33 are implemented and D-34/D-35 are not — and **D-33's implementation is now scheduled for deletion**, because Revision 2 retracts it. Of Revision 2, **nothing is implemented**: every claim in the two paragraphs above is contract, not code. Where a statement below still describes what `src/` does today rather than what the contract now says, it is marked as such.

- **0–2 — scaffolding, kernel primitives, frame slicing.** Every entrypoint in `files.json`, `realm`/`lifetimes`/`queue`/`reporter`/`failures`/`presentation`/`pointer`/`invalidation`, and the composed frame with its `DEV` assertions.
- **3–5 — the seam driver, the lifecycle, settlement.** `Transition`/`SeamOutcome`/`runCore` with both failure latches; `draggable()`, the two-phase handshake, admission, activation, the hot path, release, the cancel latch and its precedence, the failure checkpoint and the seven-step `destroy()`; the resolution attempt, the five-case `SettlementInput`, request → seal → arm, the landing completion latch and the join.
- **6 — the sortable behavior.** Every seam, `reconcileCollection`, and the single canonical `movePlaceholder()`. It also shipped `updateItems()`, which **D-44 removes** in favour of an `items()` pull source plus `controller.invalidate()`.
- **7–8 — composition and the features.** `assemble()`, the opaque feature brand — **withdrawn by D-45** — `y()`, `landing()`, `layoutAnimation()`, and `callbacks()`, `placeholder()`, `handle()`/`visual()`, which **D-56 deletes as factories** in favour of plain config keys.
- **9 — the public surface.** The export table below, frozen and asserted as an equality in `tests/exports.node.test.ts` and against the packed tarball in `tests/consumer.node.test.ts`.
- **15–17 — the sortable, completed.** D-33's declare-and-acknowledge presentation protocol (`accept({ presentation: true })` + `controller.ready(request)`) — **retracted whole by D-41**, so this is code with a scheduled deletion rather than a surviving capability; D-32's keyboard command as a complete one-slot operation sharing the pointer path's proposal protocol, which survives but must gain D-46's target policy; and `xy()`, the two-dimensional axis rule, beside the renamed `y()`.

## Demos

**This section describes the demos as they stand today — the pre-redesign ones.** They are built against the Phase 14 surface, which Revision 2 changes underneath them; nothing here has been rewritten yet, and it is recorded as what exists rather than as what the API now promises.

`src/sortable.stories.tsx` re-implements the shipped package's sortable stories against this API, under the `Drag2/Sortable` title: **List**, **Custom Placeholder** and **Zoomed Context**. Each composes `y()`, `landing()`, `layoutAnimation()` and `callbacks()` explicitly, so what the shipped package inferred from an options object is visible as installed features. The React integration in there is the **pre-redesign** one: `onReorder` returns `ReorderResolution.accept({ presentation: true })` and stores the request it was handed, and a `useLayoutEffect` calls `controller.ready(request)` once React has committed the authored order (D-33). **D-41 deletes that protocol**, and the redesigned story is an ordinary `async onReorder` that awaits its own commit and then returns `ReorderResolution.accept()` — one function, no stored request, no layout effect, no acknowledgement.

**Grid** is restored and drives `xy()` explicitly, which is the difference from the shipped story worth seeing: `@ydinjs/drag` has no axis concept at all, so its Grid story is its List story with different CSS. Here the axis rule is a named, installed feature and the two behaviours are visible side by side — the same sideways drag that `xy()` reorders, `y()` proposes nothing for.

One of the shipped package's stories still has **no drag2 equivalent**: the whole `Drag/Draggable` file — free drag with `axis`, `bounds` and `onDrop`. `draggable()` here is behavior-agnostic and requires a behavior; no free-drag behavior exists yet (plan Phases 18–20).

The List story's arrow-key hint is restored, and the rows carry `role`/`tabindex` — because `keydown` is bound on the container and must originate inside a row, so a row that cannot take focus cannot be reordered from the keyboard.

**D-46 changes the accessibility story, and it is now a stated consumer obligation rather than a story detail.** Probe E measured the current input policy and found eight of ten cases release-blocking, six of them with no drag ever activating: `preventDefault()` at admission suppresses the compatibility `mousedown`, so a nested `<button>`, `<a href>`, text input, range, `<select>` or `contenteditable` inside a row **cannot be focused, caret-placed, selected in, or operated**, while the happy-path click still fires and hides the defect. The fix is a policy, not machinery — admission declines on interactive and editable descendants, and declining already leaves native behavior completely untouched.

A `handle` resolver — now a plain config key rather than a `handle()` factory (D-56) — resolves seven of probe E's ten cases by scoping both ingresses to one grip. **It is not the accessibility answer.** Because the keyboard command is reachable only when focus is inside the resolved handle, and nothing in the library makes a handle focusable, supplying `handle` **silently removes keyboard reordering** unless the consumer makes the grip focusable itself. Probe E had to set `grip.tabIndex = 0` by hand before an arrow key admitted at all. So: **keyboard reordering must remain reachable through a deliberately focusable drag control, and providing one is the consumer's obligation.** Roles, focus order and announcements are the consumer's too; see [`accessibility.md`](../../.agents/docs/accessibility.md) §Drag.

## Migrating from `@ydinjs/drag`

The two packages are not source-compatible; this is a rewrite against a frozen contract, and this table covers the sortable — free drag has no counterpart here yet. The full boundary, per capability, is [`ledger.md`](.plan/ledger.md). The differences a consumer actually meets:

| `@ydinjs/drag` | `@ydinjs/drag2` |
| --- | --- |
| `draggable.js` | `drag.js` — behavior-agnostic, so a future free-drag consumer never imports the sortable behavior. Custom behavior authoring lives one tier down at `kernel.js` (D-48); an ordinary sortable consumer never imports it |
| one `sortable.js` barrel | `sortable.js` plus one subpath per optional feature **that installs something**; nothing is imported that is not composed |
| `sortable(container, options)` | `sortable(container, config, ...fragments)` — **one call, exactly as the shipped package had.** The pre-revision contract composed it as `draggable(container, sortable(items, …))`; D-48 gives `sortable()` the root and has it call `draggable()` internally. **This row is a parity improvement, and the only one in this table** |
| options object | **plain partial config objects**, merged by the library by config slot and materialized once after the merge (D-45), immutable for the controller's life |
| an eagerly-passed item array | `items: () => …` in the config, plus `controller.invalidate()` when the committed presentation or data may have changed. **Array identity is the structural signal**: the same identity invalidates geometry only; a new identity snapshots, reconciles and invalidates (D-44) |
| callbacks passed inline | **plain config keys** — `{ onReorder, onStart, onEnd, threshold }` written directly in the config object. **One terminal callback, `onEnd(result)`, with the four arms `accepted`/`noop`/`rejected`/`canceled`** (D-62); `onFinish` and `onCancel` do not exist. `callbacks()` existed as a factory until D-56 deleted it as an identity wrapper; the `onReorder` requirement and the `threshold` check move to the merge and now fire however the config was supplied. `readinessTimeout` went with the protocol D-41 deleted |
| a placeholder/handle options object | **plain config keys** too — `{ placeholder, handle, visual, box }`, each a callback (D-65). `placeholder()`, `handle()` and `visual()` are deleted as factories with their subpaths (D-56); `box` is new and defaults to `visual` (D-43) |
| acceptance inferred from silence, DOM mutation or elapsed time | acceptance is **explicit**: `onReorder` returns `ReorderResolution.accept()` or `.reject(reason)`, or the drop does not complete as accepted |
| errors surfaced ad hoc | one `onError(error, { domain })`, where `error` is a **`DraggableError`** carrying a coarse `code` — `'consumer' \| 'interaction' \| 'presentation' \| 'platform'` (D-64). The 14 `FAILURE_*` stages are kernel-tier vocabulary, not consumer vocabulary |
| third-party feature authoring by structural typing | **the config schema is public and stable; the installer values inside it are opaque.** A fragment is an ordinary object literal, so a consumer can spread a preset, override one slot, filter a `plugins` array, or lift `weirdThing().axis` out of a helper — none of which constructs an installer, which still requires the kernel entrypoint (D-45, D-47). `Behavior` stays opaque (D-47). This row said features were **opaque branded values** — nameable and passable, not constructible — and D-45 withdraws that brand: "public stable type whose full structure is internal and unstable" was genuinely not a coherent state, and the coherent one splits it across two levels instead of trying to make one value be both |

Behavioural differences are listed under _deliberate differences_ below.

Deliberate behavioural differences from the shipped `@ydinjs/drag`:

- `Lifetime.use()` after dispose runs the disposer immediately and reports.
- `acquirePointerCapture` lets a capture failure throw so the caller can classify it as `FAILURE_ACTIVATION` (D-17) instead of silently degrading the drag.
- `BehaviorSpec` carries a `reportFailure(stage, error)` member the frozen listing does not, because Q-1's answer for a throwing `admit` — report through `onError` with no operation — is otherwise unreachable from the kernel. See plan.md, phase 4.
- `LandingContext.from` and `.target` are **origin-relative deltas**, not viewport points, and the readiness-time `retarget(target)` receives a delta too. `anchorTarget` produces a viewport point and the kernel converts. Contract 02 shows the raw point being handed to the runner, but the runner's only writer is `compose(x, y)`, which consumes a delta from the grab rect — a point it cannot convert, because the context carries no `originRect`. The shipped package's landing plans were already in delta space.
- `acquireLift` throws when the visual's box space cannot be read — a disconnected, fragmented, or 3D-transformed visual. The shipped package flattened 3D to its 2D projection, producing a wrong lift rather than a refused one.
- **There is no authored-presentation protocol. The consumer awaits its own commit inside `onReorder`.** The order is serial — release → freeze proposal → `onReorder` → your commit → your resolution → the library restores its presentation invariants → the authoritative landing measurement → landing → terminal — so a consumer that must render before the drop lands writes `await committed` in the resolver and returns `ReorderResolution.accept()`. A synchronous consumer simply does not await, and both are one code path. **This bullet said the protocol was a declaration plus an acknowledgement** — `ReorderResolution.accept({ presentation: true })` plus `controller.ready(request)`, keyed on the request the callback was handed — because the shipped `presentationReady` promise put four obligations on the consumer whose only failure signal was a 500 ms silence (D-33). D-41 deletes both: `controller.ready()`, `ResolutionOptions`, the acknowledgement deadline and the readiness gate all go, because awaiting inside the resolver removes the window they existed to cover. A framework commit barrier is integration code, not a drag protocol.
- **A resolver that destroys the controller stops the sequence at that call** (contract I-36). The `handle` and `visual` resolvers — plain config keys since D-56 — are consumer code the behavior invokes in a sequence: `handle` then `visual` at admission, and `visual` once per candidate during a geometry rebuild. A resolver calling `destroy()` returns into the middle of that sequence, and nothing after it runs: from `handle`, admission **declines** (no operation, no `onError` — destroying your own controller is not a library failure); from `visual` at admission, admission **also** declines, so on the keyboard ingress the arrow key keeps its native meaning; from `visual` during a rebuild, no later candidate is resolved and the cache stays in the retired state teardown left it in. The shipped package's candidate rebuild has no such check and carries on.

  **Three claims in the previous version of this bullet are withdrawn, and the floor above is what survives.** (1) "**No geometry is read**" was a _ceiling_ — a promise about the whole remainder of the call graph — and D-37 withdraws it. The old quantifier ranged over every overridable member of every consumer-owned node, which contract 05 itself admits cannot be enumerated: an obligation no implementation can discharge and no review can check. What replaces it is finite and API-shaped: after logical closure the library must not **invoke a declared consumer slot**, **admit** another operation, or **publish** another lifecycle or domain event. That is a list this README's own export table already enumerates. (2) The enumeration that followed it — "the library also calls `getBoundingClientRect()` on your rows and on your placeholder, and an override of it on a custom element is your code too" — went with the ceiling, being the reach analysis D-37 retires as a proof domain. (3) "**`destroy()` is synchronous**" is now wrong: D-36 keeps it **immediate and terminal** — every guard fails from that statement onward — but if synchronous library execution is in progress, **physical teardown runs at the boundary of the outermost library transaction**, not on the closing stack. `destroy()` returns `Promise<void>` and settles once, after teardown; outside a reentrant transaction the two events still coincide, so `void controller.destroy()` remains correct for a consumer that does not care. One consequence is worth publishing on its own: **do not read `signal.aborted`, a disposed session or a detached node as an answer to "is this still alive"** — under deferral those lag logical closure (D-38).

- **Nothing native is consumed until a drag actually activates.** `preventDefault()` fires at the **activation threshold**, not at `pointerdown` (D-46, D-54), so a press that never becomes a drag leaves focus, caret, selection and form-control behavior completely intact — and admission declines outright on interactive and editable descendants. Two consequences travel with the relocation: at the threshold crossing the library **clears any selection the pre-threshold press began**, and after an **activated** drag it **suppresses exactly one subsequent `click`**, in the capture phase, so a drag that ends on a link does not also navigate. A sub-threshold press arms no suppressor. **Scroll suppression is `touch-action`, which you set in CSS** — `preventDefault()` on `pointerdown` was never a reliable scroll suppressor, and treating it as one is how a touch story silently breaks. **Evidence limit, published rather than hidden:** probe E is Chromium and mouse only; touch's long-press context menu and tap highlighting are an owed measurement, not a settled case.
- **A landing that cannot be measured is skipped, not faked** (D-49). If the authoritative measurement throws, or the precondition check finds the placeholder detached or no longer the item's sibling, the library reports through `onError`, **skips the landing animation and joins immediately**. It does not fail the drop: the DOM commit has already happened and the reorder is real, so the operation still terminates normally with its domain result. **Concretely, one operation fires `onError` once _and_ `onEnd` once** (D-62) — probe C1's defect was one terminal and `onError` **zero**, and this is what fixing it looks like (D-60). This is quality-only, and it is deliberately a jump cut — C1 measured the alternative, a confident twelve-frame flight to the viewport origin followed by a teleport back.
- **`onError` is orthogonal to the terminal** (D-60). It reports a **fault class**, not an operation outcome, so **do not write `onError` and `onEnd` as mutually exclusive** — no `else`, no "if it errored it did not finish". `FAILURE_LANDING_TARGET` under D-49 is the first stage that is classified, **non-consequential and has no recovery**: the settlement is not failed and the domain result stands. The package used to carry an unstated `onError ⇒ consequential` assumption that nothing had ever tested; D-49 falsifies it, so it is written down here rather than left for a consumer to re-derive from a surprising pair of callbacks.
- **The axis rule is a named, installed feature**, and there are two: `y()` for a column and `xy()` for a wrapping field. The shipped package has no axis concept at all — its `nearestSlot` is a 2-D search — so `y()` is a _narrowing_ of shipped behavior and `xy()` restores the shipped default explicitly (ledger L-8).

## Geometry

There is no coordinate module here. All geometry goes through `@ydinjs/box-quad`, which owns the single flat-tree traversal and the single coordinate model for transforms, ancestor zoom, shadow DOM and the supported 3D cases.

`acquireLift` measures the visual **once** with `coordinates()` and takes everything from that one `Box`: the composed element→viewport matrix (the faithful mode's base transform), the untransformed border-box size (both lifted modes' fixed box), the inherited zoom the top layer does not escape, and the inherited linear basis the in-place mode inverts. The shipped package made two independent traversals for the first two and derived the third from `item.offsetParent`, which stops at a shadow boundary and is `null` for a fixed-position visual.

The in-place mode inverts the **inherited** basis rather than the visual's own space, because its translate is prepended to the visual's authored transform and so is scaled only by what the visual inherits. No flat-tree, shadow-root or `display: contents` knowledge lives in this package — box-quad produces that basis during the traversal it already performs.

One consequence worth noting against contract F-24: `compose` is now allocation-free in **every** lift mode, including in-place. The shipped in-place path allocated a `{ x, y }` projection per pointer sample.

## Export topology

The subpaths in `files.json` are declared before the modules they name exist rather than grown as features arrive. That is a measurement precondition: it makes each composition's import graph physically unable to reach a feature it did not select, independent of bundler heuristics (contract 03 §The export topology this requires). Eight were frozen at phase 0 and `sortable/xy.js` was the one addition, making nine; **Revision 2 removes three and adds one, so the net is 9 → 7**, for the reasons below.

| Subpath | Runtime | Types |
| --- | --- | --- |
| `drag.js` — **shared vocabulary** | `DraggableError` | `DraggableErrorCode`, `Point`, `DOMRealm` |
| `kernel.js` — **the kernel tier**, new (D-48) | `draggable`, the 14 `FAILURE_*` constants (D-64) | `BehaviorFactory`, `FailureStage` and the behavior-construction types |
| `sortable/feature.js` — **the middle tier**, new (D-61) | — | `SortableInstaller`, `FeatureContext`, `SortableContribution`, `InsertionGeometry`, `DisplacementHook`, `LandingStart`, `LandingContext`, `LandingHandle` |
| `sortable.js` | `sortable` (takes `root`, returns a `SortableController` directly), `ReorderResolution`, `AT_PROPOSAL`, `AT_CONSUMER` | `SortableConfig`, `SortableController`, `OnReorder`, `PlaceholderContext`, `CancelStage`, `DragErrorContext`, `ReorderRequest`, `ReorderProposal`, `CollectionSnapshot`, `PlaceholderFactory`, `ReorderResolution` and its two members, the four result types and their two unions |
| `sortable/y.js` | `y` | — |
| `sortable/xy.js` | `xy` | — |
| `sortable/landing.js` | `landing` | `LandingOptions` — `{ duration?, easing? }`; **no `run`** (D-63) |
| `sortable/layout-animation.js` | `layoutAnimation` | `LayoutAnimationOptions` |

Every type a public type structurally depends on is exported, rather than left reachable-but-unnameable: that is why `DOMRealm`, `Point`, `CollectionSnapshot` and `PlaceholderFactory` are on the list — and why `FailureStage` is on the **kernel** entry's list rather than this one since D-64, by the same rule applied at the tier that now depends on it. TypeDoc emits **zero** unresolved-reference warnings across the entries, and none are suppressed — a warning there means a public type depends on something a consumer cannot name.

**An ordinary sortable consumer imports from `sortable.js` and `drag.js` only, and never needs `@ydinjs/drag/kernel` — nor `sortable/feature.js`, which is the rung above them (D-61).** That is the progressive-disclosure promise contract 00 §11 makes, and D-48 makes it true **by construction rather than by convention**: `sortable()` and `freeDrag()` take the root themselves, call `draggable()` internally and return their controllers, so the kernel tier is reachable but never on the ordinary path.

**`drag.js` keeps its current job; its original rationale did not survive, and the entry did (D-64).** The stages it was justified by are now kernel-tier, and what keeps it is `DraggableError` — a **class**, so a runtime value both tiers must name and neither owns. It is behavior-agnostic shared vocabulary — the error class, `Point`, `DOMRealm` — so a future free-drag consumer still never imports the sortable behavior, which is exactly why it was carved out at phase 0. It is **not** the kernel tier: `sortable.js`'s `onError(error, { stage, domain })` structurally depends on `FailureStage` and the `FAILURE_*` constants, so putting them behind `@ydinjs/drag/kernel` would force an ordinary consumer to import from the kernel to `switch` on an error stage their own handler was handed — precisely the inversion D-47 exists to prevent. Shared vocabulary belongs to neither tier, so it gets its own home instead of lodging in whichever tier also happens to need it. `draggable()` and the authoring types move to a **new `kernel.js`**, where D-47's `draggable(root, (host) => ({ spec, controller }))` is literally the supported form.

**Four factories go and three subpaths go with them, and that strengthens the measurement argument rather than weakening it.** D-56 removes `sortable/callbacks.js`, `sortable/placeholder.js` and `sortable/handle.js` — three subpaths, because `handle()` and `visual()` shared one — so `callbacks()`, `placeholder()`, `handle()` and `visual()` become plain config keys written directly in the config object: `{ onReorder, threshold, createPlaceholder, handle, visual, box }`. Under D-45 those four had already become identity wrappers returning a public config slot, which voids the reason their subpaths existed at all: **a subpath carrying no runtime machinery measures nothing.** The surviving fragment factories are exactly the four that install something — `y()`, `xy()`, `landing()`, `layoutAnimation()` — and each still owns a subpath that carries real code. **Validation is not lost:** `callbacks()`'s construction-time `onReorder` requirement and `threshold` check move to the merge, alongside D-45's missing-axis check, where they now fire for a config supplied any way at all rather than only through a factory.

**Revision 2.1 adds a subpath rather than removing one, and it is the first that does.** `sortable/feature.js` publishes the installer vocabulary so a third party can author a custom axis, landing or plugin **without dropping to the kernel tier and rewriting the sortable** (D-61). It has no runtime exports at all, so it makes no isolation claim and cannot move the measurement in either direction — unlike the three D-56 deleted, which claimed one and delivered none.

**Two more types leave, and the `SortableController` surface changes with them.** `SortableFeature (opaque)` goes: D-45 withdraws the feature brand, so a fragment is a plain partial config object and there is no branded value left to name. `ResolutionOptions` goes: D-41 deletes `accept({ presentation: true })`, so the resolution takes no options. **`LandingHandle.retarget` is removed** — D-41 deletes its only producer, and the package must not publish a member the library never invokes; probe C1 separately showed it was a hazard, since `landing()` documents it as optional and a conforming runner that omitted it animated toward a stale target for the whole landing. On the controller, **`updateItems()` goes and `invalidate()` arrives** (D-44) — the collection is delivered as an `items()` pull source in the config plus a payload-free `controller.invalidate()`, and the name deliberately collides with the feature-owned geometry `invalidate()`: the controller member is the **cause**, the geometry slot the **effect**. `Behavior (opaque)` **stays** opaque (D-47); D-45 is not a licence to unbrand it, and the low-level handshake stays public and factory-shaped, because the host must exist before a behavior can build host-backed state while ingress must not arm until spec and controller have been returned.

**Every line in the paragraph above is contract, not shipped code.** The frozen equality in `tests/exports.node.test.ts` still asserts the Phase 14 table, and updating it is implementation work with its own phase.

Everything the kernel and a behavior say to each other — `BehaviorSpec`, `KernelHost`, every seam, scope, contribution and slot type, and the phase/lift/outcome/recovery constants — is internal, unstable, and reaches no entry module. The consumer fixture asserts each one is unreachable, and a `@ts-expect-error` that stops erroring fails the build, so the list cannot rot into a no-op.

### Option domains

| Option | Unit | Domain | Default |
| --- | --- | --- | --- |
| `threshold` (config key) | CSS px | finite, `>= 0` | `8` |
| ~~`callbacks({ readinessTimeout })`~~ | ~~ms~~ | ~~finite, `>= 1`~~ | ~~`500`~~ — **removed by D-41** |
| `landing({ duration })` | ms | finite, `>= 0`; or `({ distance, from, to }) => number` returning one (D-67) | `200` |
| `layoutAnimation({ duration })` | ms | finite, `>= 0` | `160` |

Each throws a `TypeError` on a value outside the domain, so a `NaN` threshold fails at the call that introduced it rather than as a drag that never activates. ~~**One documented exception:** `landing({ run })` replaces the built-in runner outright, so `duration` and `easing` have nothing left to configure and are neither read nor checked — `landing({ duration: -1, run })` does not throw.~~ **D-63 deletes `run` and the exception with it**: both options are now always read and always validated, so the rule above has no exceptions at all.

**Where the check runs follows when the value exists.** A fixed option is validated **at construction**, once, before any drag — and for `threshold`, "construction" now means **the merge** rather than a `callbacks()` call, so it is checked however the config reached the library (D-56). `landing({ duration })` additionally accepts a **thunk**, whose result does not exist until the landing opens: it is invoked and validated **once per landing**, at settlement — the moment the shipped package read `landingTiming()` — so a distance-scaled or per-drop duration keeps the default runner instead of replacing it. A thunk is checked for being a function at construction; its _result_ is checked at settlement, ahead of the reduced-motion collapse, so an invalid or thrown result is reported under `prefers-reduced-motion: reduce` exactly as it is without.

`easing` is not validated: it is a CSS easing function and the platform is the only correct parser for one.

`readinessTimeout` was a **failure bound, not a schedule** — exceeding it was `FAILURE_PRESENTATION_READY` and replaced the settlement. It bounded a silence that can no longer occur: with the commit awaited inside `onReorder` there is no separate acknowledgement to wait for, so **the only bound on a consumer's own commit is the one the consumer writes**, and an `await` that never settles keeps the operation open until a cancel or a `destroy()` ends it. That is ordinary Promise behavior with ordinary failure semantics, which is what D-41 traded four opaque consumer obligations for.

## Size budgets

Baselined 2026-08-02 (M-3 — `.plan/measurements/m3.md`), re-measured **2026-08-08** at Checkpoint D and again after each of its four reviews. `just size` runs `bench/size/measure.ts`, where each composition is one declaration: the exact named imports a consumer writes, a budget, and the modules its graph must and must not contain. Five compositions, not four: Phase 17's second axis is a peer rather than an assumed equal, so `minimal (xy)` is measured. The growth over the M-3 baseline is accounted for — D-33's settlement protocol (+70 B), Phase 16's keyboard ingress (~300 B, deliberately not tree-shakeable), Phase 17's shared rect index (+60 B), Checkpoint D's fixes (+40 B) and its second review's terminal barrier (+30 B to +90 B, composition-dependent), its third review's abort return channel (±20 B, inside brotli's noise band) and its fourth review's completion of that barrier (+37 B minimal, +70 B with `layoutAnimation()`, +70 B complete). Every composition is still inside the budget it already had — no budget was re-based for the fourth review — with **0.11–0.16 kB of headroom against budgets originally set with ~0.3 kB**, tightest on `+ layoutAnimation` and `complete`. Phase 21 re-bases rather than absorbing again.

The import maps _are_ the measurement, and the graph half is why this is not a `size-limit` config: a byte delta cannot tell "absent" from "present and mostly shaken" (`.agents/docs/measure/brief.md`). The two baselines are checked-in modules under `bench/size/`, because neither is expressible as a set of imports.

**The two baselines answer different questions and are never substituted for each other.** A costs 0.27 kB less than `complete` with the same features — 266 B exactly, 2.5% — and that is what composition costs. B is 3.23 kB smaller than `minimal` — 3,227 B exactly — and is not feature-equivalent to anything here: that is what migrating costs. Both come from the same `just size` run as the table above; the exact bytes are quoted because every earlier revision of this paragraph published a rounded figure that was stale on arrival.

`tests/bench/size.node.test.ts` runs the same declarations in CI, plus a determinism check and a fidelity check that the hand-written non-composed baseline still fills exactly the slots `assemble()` fills.

**Revision 2 re-bases nothing here yet, and one number should be set against it in advance.** Probe A spiked D-36's transaction bracket against the current source and measured **+500 / −491 lines across 13 source files** — near-neutral, and near-neutral in _lines_, which is not the same axis as brotli. **The bracket is a complexity and invariant win, not a size win, and this package does not claim a size benefit from it.** What it buys is stated in D-37: a guard exists to stop work that would outlive the close, and work the bracket undoes at the transaction boundary has no consequence to stop — which is what lets 27 of 33 statement-level liveness readings retire. Whatever Revision 2 costs in bytes is Phase 21's re-base to measure, on the same `just size` declarations as the table above.
