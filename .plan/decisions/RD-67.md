#### RD-67 — The coordinator reads each session's context size from a file that the owner's status line writes, and tells the owner at a task's end when the session can be cleared

**Decided 2026-11-26 by the architect, on `repo/session-context-1`,** on the owner's answers of the same day to the three questions of the [plan](../session-context-1/session-context-plan.md), relayed by the coordinator. His words are in the plan's [questions](../session-context-1/session-context-plan.md#questions-for-the-owner). The plan's readings, its reasons and its `SC-1` to `SC-7` stand where this decision doesn't change them. Where the two differ, this decision applies. `RD-66` (`repo/mutations-1`) is the highest `RD-` on any branch on `origin`. **Implemented in the same pull request** by [coordinator-setup.md](../../.agents/docs/coordinator-setup.md) §Direct send step 5 and §Context readings, and [the coordinator's role definition](../../.claude/agents/coordinator.md) §Sessions. Until the owner adds property 2's lines to his script, every reading is no reading.

**Where it comes from.** The owner doesn't want autocompact, which _"fires in the middle of a session"_, and would rather clear a session between tasks. Nothing lets one session or a script clear another, so the clear stays his keystroke. The coordinator can make the boundary visible and keep it open.

**Properties:**

1. **The file.** Each status line run of a named session replaces `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/ctx/<session_name>.json`, with a `/` in the name written as `_`, through a temporary file in the same directory and a rename. It holds the payload's `session_name`, `session_id`, `transcript_path` and `cwd`, `written_at` in seconds since the epoch, and `context_window`'s `total_input_tokens`, `context_window_size` and `used_percentage`. A payload without `session_name` writes nothing. (`SC-1`.)
2. **The writer is the owner's,** as lines of his own status line script. The repository's `.claude/settings.json` sets no `statusLine`. The lines, the file's format and the reading command are in [coordinator-setup.md](../../.agents/docs/coordinator-setup.md) §Context readings, and when the owner changes the lines he changes that section. (`SC-2`.)
3. **The reading.** When a role's closing message arrives, the coordinator reads that session's file. A reading is valid when it was written after the coordinator sent the task. An older file, or none, is no reading: the coordinator tells the owner so once for that session, and doesn't ask the session. (`SC-3`.)
4. **When the coordinator tells the owner that a session can be cleared:** at a closing message that ends the session's part of a unit, and at a closing message whose reading shows more than 300,000 `total_input_tokens`. It says so in one line, in the owner's language, and names no size, for example _"Mx Implementer B: the unit is closed, the session can be cleared."_ It never says so in the middle of a task, and it says nothing about a session's size otherwise.
5. **The hold.** After that line, the coordinator holds that session's next task until the session's file shows the clear, which is a `session_id` other than the reading's or a `total_input_tokens` of 0, or the owner tells it to send. It checks the file when it next acts, and doesn't poll. It routes the other sessions' work meanwhile. The owner's word releases one hold: at the next closing message, property 4 applies again.
6. **The coordinator's own size.** At each owner checkpoint, the coordinator reads `Mx Coordinator.json`, and when it shows more than 300,000 `total_input_tokens`, tells the owner in the same line that the coordinator can be cleared. Nothing is held: the coordinator is already waiting for him. Its state after a clear is in the repository and the work queue. (`SC-5`.)
7. **Limits.** A session on another machine, without a name, or without a status line run since the owner's change writes no file. A Claude Code upgrade that renames a payload field writes `null`, and nothing checks the format. Two live sessions with one name would write one file, which [Session names](../../.agents/docs/coordinator-setup.md#session-names) already forbids. A cancelled run can leave a `.tmp.*` file in `ctx/`, which nothing reads. (`SC-7`.)
8. **Idle compaction isn't part of this decision.** The owner's answer to Q3: it is compaction while a session is idle, which he knows and is still weighing, and it isn't what he meant. Whether it is on is his setting.

**Readings of the answers,** the architect's, for the owner to correct:

- **Q1, _"Да"_,** adopts the hold at a unit's end (property 5).
- **Q2's _"контекст упоминать не надо"_ ("there's no need to mention the context")** is read for every message about a session, the unit's end included: the owner asked to be told that a session can be cleared, and its size adds nothing he acts on. So the plan's _"555k (55%)"_ goes from the example, and the 50% mention inside a unit goes.
- **Q2's _"300к"_** is 300,000 `total_input_tokens`, an absolute number and not a share of the window. _"при превышении"_ ("on exceeding") is more than 300,000. The coordinator sees the size only at a closing message, so _"дождёшься её окончания"_ ("wait for the task to end") is property 4's closing message.
- **Q2 holds the next task, as Q1 does (property 5).** The owner didn't say "hold" in Q2. Without the hold, the line _"the session can be cleared"_ arrives when the coordinator has already sent the next task, and a clear then lands in the middle of a task, which is what he asked to avoid. With it, he keeps the context of a session he doesn't want cleared by one word.
- **Every closing message above 300,000 tells him again,** and not only the one at which the size first passes it. The rule then needs no memory of earlier readings, which the coordinator loses at its own clear, and a session that the owner kept goes on growing.
- **The coordinator's own size takes the same 300,000** (property 6). Q2 asked about both.

**What it supersedes:**

- [coordinator-setup.md](../../.agents/docs/coordinator-setup.md) §Direct send, step 5, which said: _"Clear a session whenever you choose. The coordinator cannot see or reset another session's context and does not wait for a clear. A cleared session keeps accepting the coordinator's prompts, so step 3's message is not sent again."_
- [The coordinator's role definition](../../.claude/agents/coordinator.md) §Sessions, whose last paragraph said: _"You cannot read another session's context size or clear it: `/clear` sent with `SendMessage` arrives as text. Send the next task without waiting for a clear; the owner clears a session at their own discretion."_

Both came in at `a07739742` (#25), with no record. The plan's _Why_ paragraphs give the reasons for properties 1 to 3.

**Costs.** Eleven lines in the owner's script, once, and about 15 ms per status line run ([`writer.txt`](../session-context-1/checks/writer.txt)). One command per closing message and per owner checkpoint, about a hundred tokens each. A slot whose unit has ended, or whose session is past 300,000 tokens at a task's end, waits for the owner's `/clear` or his word. The other slots don't wait.

**Not adopted:**

- **The size in the message** (the plan's SC-4 example). Q2.
- **A share of the window.** The plan proposed 50%. The owner gave 300k, and an absolute number stays the same number when a model's window changes.
- **Telling only when the size first passes 300,000.** It needs the earlier reading, which the coordinator loses at its own clear, and the owner's kept session isn't reminded as it grows.
- **Telling without holding inside a unit.** The next task would reach the session before the clear.
- **A tracked status line in the project's settings, a tracked writer called by his script, and the transcript** (the plan's SC-2).
