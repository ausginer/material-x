#### RD-66 — A dispatched run reads its mutation file with the runner, every run applies its mutations in a worktree that it creates, and a row that didn't run has no verdict

**Decided 2026-11-26 by the architect,** on #301's feature proof by Mx Reviewer B ([`feature-proof-claude.md`](../reviews/mutations-1/feature-proof-claude.md), read at `9a65f1a89`), findings `reviewer-3`, `reviewer-4` and `reviewer-1`. The coordinator requested the rulings. Written on `repo/mutations-1` at `f8fb96ce2`. `RD-65` is the highest `RD-` on any branch on `origin`. It supersedes parts of `RD-65`, which the note at the end of `RD-65` lists. It needs no new ref, tag or branch.

**Properties:**

1. **A dispatched run reads the mutation file from the ref that it is dispatched on,** together with the runner and the config (`RD-65` property 3). The code under test, its lockfile and its engines come from `ref`, and `ref` doesn't have to hold the file. A local run already does this (`RD-65` property 8): it reads the file from the working tree and runs the code at `--ref`. The summary of a dispatched run names two commits: the commit whose code ran, and the commit that the file and the runner came from.
2. **`run` has no `--workdir`.** Every run applies its mutations in a detached worktree of the commit that the run creates in a temporary directory, locally and in CI. A CI leg runs the tool from its checkout of `ref`, and the tool treats that checkout as an invoking checkout: it reads it and never writes to it. `run` accepts `--ref`, `--engine`, `--only`, `--config`, `--shard`, `--report` and `--summary`. None of these options applies a mutation outside the copy.
3. **A row that ran unmutated and doesn't run with the mutation has no verdict in that engine,** like a row that the unmutated run already fails. Such a row counts neither as failed nor as passed. There are still four outcomes, and _void_ now means that a selected row has no verdict in that engine:
   - **A _fails_ expectation:** _void_ when a selected row has no verdict, else _missed_ when a selected row passed, else _as expected_. _Void_ takes precedence over _missed_, as it does in the current code.
   - **A _survives_ expectation:** _caught_ when a row failed, else _void_ when a row that passed unmutated has no verdict, else _as expected_.
   - **The report and the summary say why each such row has no verdict:** it failed unmutated, or it didn't run. For a row that didn't run, they give the reason that Vitest reported for its file, such as a load error or a browser that didn't start.
   - **The engines' comparison (`RD-65` property 6) counts only rows that have a verdict in each engine compared.**
4. **The acceptance dispatch that is owed after the merge** runs on `main`, with `ref: 9173a25a1` and `file: .plan/mutations-1/acceptance/rf-142.mutations.ts`, in the three engines. Its outcomes and flags are recorded as information, as `RD-65` property 10 says. Its summary names `9173a25a1` as the commit run and `main`'s commit as the file's commit. The file was first committed in `ef6a78b93`. The proof says `9a65f1a89`, but `git log --diff-filter=A` returns `ef6a78b93`, and `9173a25a1` doesn't hold the file. The stale-edit witness stays as the proof records it: `ref: main` and `file: .plan/mutations-1/acceptance/stale.mutations.ts`.

**Why, property 1 (`reviewer-3`).** MU-7 lets an older commit run so that the acceptance run can use one. But MU-7's input description, _"`ref`: the commit to run, which holds the mutation file"_, rules that out for any file written after the commit it tests. The RF-142 file is such a file. The local CLI already separates the two commits, so property 1 makes CI do the same. The runner, the config and the file are the reviewer's side of the run, and `ref` is the code under test.

- **Rejected: an input that names the file's commit.** It gives the reviewer a third commit to choose. The dispatch ref already carries the runner and the config, and the file belongs with them.
- **Rejected: a branch or tag at `9173a25a1` with the file added.** It would need the owner's word, and it fixes only this run. Under MU-7's wording, every review would also have to run at its own record commit instead of the head that it read.
- **Rejected: `ref: main`.** It runs code that isn't `9173a25a1`'s: 34 files under `packages/material-x` and `packages/core` differ. Such a run would pass and look like the acceptance run.

**Why, property 2 (`reviewer-4`).** The leg's `--workdir .` names the invoking checkout itself, so a check on the named directory can't tell CI's disposable checkout from a reviewer's tree. A check that the directory is at the commit and clean would fix P4's false _missed_, but not P3c, where a signal leaves the mutation applied. The option saves one worktree and one install from the cached store per leg. That is seconds, against MU-7's estimate of 2 minutes of setup and 10 to 21 minutes of mutations per leg. Without the option, property 4 holds for every option that the CLI accepts, and CI and a local run use the same code path (property 8: _"gives the same reports"_). The feature proof accepted `--shard`, `--report` and `--summary`, so property 2 lists them.

**Why, property 3 (`reviewer-1`).** _Missed_ says that a selected row passed, and a row that didn't run didn't pass. The current code reads it as failed, so a broken import gives a false kill, and `RD-62` property 5 asks a review to rule that out. _Void_ already means _"the row has no verdict there"_, and the workflow already fails on it. A fifth outcome would add a name, but the reviewer would do nothing different with it, so this decision widens _void_ instead. The report says which of the two cases it is, so the summary can tell a broken import from a removed mechanism.

- **The rule.** A run is one entry of the file's `runs`. In each engine, after the engine's unmutated run and before any mutation is applied, the file is refused with 2 when Vitest's report for one of its runs lists no test file. This holds for any expectations: a file with only _survives_ expectations, a file in which another run lists test files, and a file whose _fails_ selectors point into the run. With it, `RD-65` property 5's sentence reads: _"A run that selects no test file in an engine's unmutated run, or a selector that covers no row of that run, makes the file invalid."_
- **What the refusal names:** each such run, by its directory and its tests, and the engine. The selector refusal still names each selector that covers no row. A selector into a run that this refusal names may be listed or left out.
- **Its boundary.** The refusal reads only whether a run's report lists a test file. A listed test file that has no row unmutated, such as one that fails to load, isn't refused by it: a selector into it is refused as before, and a survivor is judged on the rows that ran. A listed test file whose engine didn't run it is still a failure outside the tests, with 3. A mutated run is never refused: a row that ran unmutated and doesn't run with the mutation is _void_, by property 3. Every leg runs the unmutated runs, so each shard refuses the file the same way, and `mutations.yml` already records a leg's exit 2 as a refusal.
- **Why (a), not (b).** The reasons are those of the note above. (b) refuses only a file whose whole unmutated run has no row, so a mistyped `tests` in one run of a file with several runs still reads _as expected_ on no row of that run.
