#### RD-68 — The pull request that implements a decision updates its status sentence, and the sentence names no merge

**Decided 2026-11-27 by the architect, on `repo/decision-status-1`,** on the owner's approval of the same day, relayed by the coordinator: _"docs PR - да, давай сделаем"_ ("docs PR — yes, let's do it"). The architect proposed this unit in closing fp-3 of #321's [feature proof](https://github.com/ausginer/material-x/blob/ee41855dc/.plan/reviews/use-sortable-1/feature-proof-claude.md), on `material-x/use-sortable-1`, where `RD-52` and `RD-60` still said _"Unimplemented"_ after their units. `RD-67` is the highest `RD-` on any branch on `origin`, so this is the next free number. **Implemented** by #329: the rule in [`documentation.md`](../../.agents/docs/documentation.md#a-decisions-status) §6, its pointer in [`handoff.md`](../../.agents/docs/handoff.md#record-the-handoff), and the audit below.

**Amended 2026-11-27, before merge,** by the architect, on `proof-1` and `proof-2` of #329's [feature proof](../reviews/decision-status-1/feature-proof-claude.md) at `3a40b6908`. A status names no branch: the implementer adds _"**Implemented** by #N"_ in a commit after it opens the pull request. Only the implementing branch is barred from naming a merge, and a sentence written after the merge, as this audit's are, names the merge it read. Properties 2 and 3 changed, and the branch form is under _Not adopted_. Implemented by #329 with the decision. What they said before is at the end.

**Properties:**

1. **Where a status is.** A decision's status is a sentence in the paragraph after its heading. An amendment's status is in the amendment's own paragraph. A dated note is history, and isn't updated.
2. **Who updates it, and when.** The pull request that implements a decision, or one of its amendments, adds _"**Implemented** by #N"_ after the sentence. The implementer adds it in a commit after it opens the pull request, because the number doesn't exist before, and until then the sentence stays unimplemented. When the pull request implements only part, it says which part. The implementer makes this edit, because it is non-substantive (`documentation.md` §6, _A decision is atomic_). The commit changes only a record, so it can carry `[noci]` (`RD-15`).
3. **The implementing branch names no merge.** Its sentence travels with the implementation, so it is on `main` exactly when the implementation is, and never if the pull request closes unmerged. _"Not yet merged"_, _"when #N merges"_ and a merge commit, which the branch can't know, are what went stale here. A sentence written after the merge, when an audit corrects a stale status, names the merge it read, as _"**Implemented** by #N, merged <date> as `<commit>`"_. That merge has happened, so the sentence stays true.
4. **A decision that holds without code** is updated by whoever records that it holds.
5. **A review reads the sentence,** and an implementing pull request that leaves its status unimplemented has a finding.
6. **Where it is written:** `documentation.md` §6, _A decision's status_, with a row in §9. `handoff.md` §Record the handoff names it among what a finalized handoff identifies, because an implementer reads that document before committing and may never read `documentation.md`.

**Why.** No rule said who updates a decision's status, or when. So a status was written when the decision was made, or when its branch was implemented, in terms of a merge that hadn't happened yet, and nobody came back after the merge. A correction made after the merge is a second change for every merge, and nobody owns it. A sentence that the implementing branch writes is true on the branch and on `main` alike, and needs no one after the merge.

**Not adopted:**

- **The coordinator updates the status after each merge.** That is a commit and a pull request per merge, by a role that doesn't write the record, and a merge it misses goes stale as before.
- **A status derived from GitHub's state by a script.** A reader of the decision file would then need to run something to learn its status, and the file would still carry a sentence that could disagree with the script. One sentence that the implementing branch writes needs neither.
- **A status table.** `RD-64` removed drag's, because every decision changed its one line.
- **The branch form, _"on `<branch>`"_, while the pull request has no number** (`proof-2`). The implementing commit usually comes before the number, because `AGENTS.md` opens a pull request once the unit is pushed, so the branch form reached `main` unless someone came back to replace it, and no one was named to. On `main` it names a branch that is deleted on merge, and the branch that holds a work item is queue state (`work-queue.md`). A commit after the pull request opens costs a reduced run.
- **Strip the merge commit from the audit's 28 sentences** (`proof-1`). Each is true, and its commit lets a reader with only `git` find the merge. `RD-6`'s status on #72 already named its merge commit after the merge. What property 3 guards against is a merge named before it happens.
