#### RD-68 — The pull request that implements a decision updates its status sentence, and the sentence names no merge

**Decided 2026-11-27 by the architect, on `repo/decision-status-1`,** on the owner's approval of the same day, relayed by the coordinator: _"docs PR - да, давай сделаем"_ ("docs PR — yes, let's do it"). The architect proposed this unit in closing fp-3 of #321's [feature proof](https://github.com/ausginer/material-x/blob/ee41855dc/.plan/reviews/use-sortable-1/feature-proof-claude.md), on `material-x/use-sortable-1`, where `RD-52` and `RD-60` still said _"Unimplemented"_ after their units. `RD-67` is the highest `RD-` on any branch on `origin`, so this is the next free number. **Implemented** on `repo/decision-status-1`: the rule in [`documentation.md`](../../.agents/docs/documentation.md#a-decisions-status) §6, its pointer in [`handoff.md`](../../.agents/docs/handoff.md#record-the-handoff), and the audit below.

**Properties:**

1. **Where a status is.** A decision's status is a sentence in the paragraph after its heading. An amendment's status is in the amendment's own paragraph. A dated note is history, and isn't updated.
2. **Who updates it, and when.** The pull request that implements a decision, or one of its amendments, adds _"**Implemented** by #N"_ after the sentence, or _"on `<branch>`"_ while the pull request has no number. When it implements only part, it says which part. The implementer makes this edit, because it is non-substantive (`documentation.md` §6, _A decision is atomic_).
3. **No merge is named.** The sentence travels with the implementation, so it is on `main` exactly when the implementation is, and never if the pull request closes unmerged. _"Not yet merged"_, _"when #N merges"_ and a merge commit are what went stale here.
4. **A decision that holds without code** is updated by whoever records that it holds.
5. **A review reads the sentence,** and an implementing pull request that leaves its status unimplemented has a finding.
6. **Where it is written:** `documentation.md` §6, _A decision's status_, with a row in §9. `handoff.md` §Record the handoff names it among what a finalized handoff identifies, because an implementer reads that document before committing and may never read `documentation.md`.

**Why.** No rule said who updates a decision's status, or when. So a status was written when the decision was made, or when its branch was implemented, in terms of a merge that hadn't happened yet, and nobody came back after the merge. A correction made after the merge is a second change for every merge, and nobody owns it. A sentence that the implementing branch writes is true on the branch and on `main` alike, and needs no one after the merge.

**Not adopted:**

- **The coordinator updates the status after each merge.** That is a commit and a pull request per merge, by a role that doesn't write the record, and a merge it misses goes stale as before.
- **A status derived from GitHub's state by a script.** A reader of the decision file would then need to run something to learn its status, and the file would still carry a sentence that could disagree with the script. One sentence that the implementing branch writes needs neither.
- **A status table.** `RD-64` removed drag's, because every decision changed its one line.
