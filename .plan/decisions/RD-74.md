#### RD-74 — `useClickActivation`, `useFormActivation` and `parseMs` move from material-x to `@ydinjs/core`

**Decided 2026-11-27 by the architect, on `repo/core-placement-1`,** on the owner's acceptance of step (c)'s [plan](../core-placement-1/core-placement-plan.md) at his checkpoint of the same day, relayed by the coordinator, with [Q2](../core-placement-1/core-placement-plan.md#q2--useformactivation) (a). The plan proposed it as `CP-D3`. `RD-73` is the step's first decision, on this branch, and `RD-72` is reserved for `material-x/select-1`. **Unimplemented.** The plan's [unit 1](../core-placement-1/core-placement-plan.md#unit-1--attributeclaimer-and-the-moves) is ready for an implementer. **Implemented** by #345.

**The owner's words,** translated by the coordinator from Mx Architect Explainer's notes, 2026-11-26: _"useClickActivation & parseMs — yes."_ The `useContext` wrapper stays, _"on purpose, in case a user wants to use, for example, signals"_. Explainer's list didn't name `useFormActivation`. At his checkpoint the owner answered Q2 with (a): it moves with `useClickActivation`.

**Properties:**

1. **`useClickActivation`** moves to `@ydinjs/core/controllers/useClickActivation.js`, as a controller of its own, as each core controller is. **`useFormActivation`** moves to `@ydinjs/core/controllers/useFormActivation.js`, and its JSDoc names the click that `useClickActivation` cancels. material-x's `src/core/utils/events.ts` is then deleted.
2. **`parseMs`** moves to `@ydinjs/core/controllers/useCSSProps.js`, beside `CSSPropParser` and `CSSVariableError`. It is the parser for that controller, so a consumer imports it from where it uses it. `identity` stays in material-x's `src/core/utils/fns.ts`, as a one-line function.
3. **Each moved function keeps its behavior and signature,** and material-x's call sites change only their import: `SwitchCore.ts` and `CheckableCore.ts` for `useClickActivation`, `button.ts` and `icon-button.ts` for `useFormActivation`, and `ripple.ts` and `useSortable.ts` for `parseMs`.
4. **The `useContext` wrapper stays** in material-x's `src/core/utils/useContext.ts`, so that core's `useContext` stays neutral about how a value is carried.
5. **No re-export is left** at the old paths (`CONTRIBUTING.md` §8). `@ydinjs/core` is unpublished, so its shape is free.
6. **Each is public core API:** entries in `files.json` and `docs/api.ts`, rows in the README's tables, and core rows: the plan's unit 1, _Rows, in core's browser project_.

**Why.** Each passes the owner's test of what core is for (`RD-75` property 1). Any custom element that delegates activation to a native control in its shadow tree needs `useClickActivation`, and any form-associated button needs `useFormActivation` to submit or reset its form through `ElementInternals`. `useFormActivation` skips a click whose default was prevented, which is the host click that `useClickActivation` cancels, so the two are one sequence and move together. It uses `Typeable` and `internals`, which are core's. `parseMs` reads a CSS time for `useCSSProps`, and names nothing of material-x.

**Not adopted:**

- **Q2 (b), `useFormActivation` stays in material-x,** as the owner's _"yes"_ named only `useClickActivation`. Then the two halves of one sequence would be in two packages.
- **`parseMs` in a new `@ydinjs/core/utils/` module.** It would be a module for one function that only `useCSSProps` calls.
