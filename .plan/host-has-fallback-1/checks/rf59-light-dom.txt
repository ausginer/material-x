# Reading.
#
#                                          Chromium 158     Firefox 159              WebKit 27.2
#   CSS.supports(:host(:has(> [slot])))    false            true                     true
#   :host(:has(> [slot=lead])) matches     never            only when the host's     yes, and follows every
#                                                           own style is computed:   change (append, remove,
#                                                           stale after a light-DOM  slot attribute, inside a
#                                                           change until the host    shadow tree, combined)
#                                                           is re-inserted
#   :has-slotted matches                   no               yes, and follows changes no
#   :host:has(<shadow>) matches            yes              no (supports() says yes) yes
#
# So no engine matches `:host:has(.x:has-slotted)` as written: Chromium and WebKit lack `:has-slotted`, and Firefox
# lacks `:host:has()`. Chromium matches neither `:has-slotted` nor `:host(:has())`, so no CSS selector tells
# Chromium 158 that a slot has content: it needs the runtime's class. Firefox's `:host(:has())` goes stale, which is
# worse than no match. The owner's recollection (":host(:has()) works in Firefox and Safari, :has-slotted works in
# Chrome") holds for WebKit's `:host(:has())` only.
#
# What `:host(:has(> [slot=x]))` would also miss, in WebKit where it works:
#   - the default slot: `:not([slot])` sees element children only, never text, and the list item's label is often
#     text. Its `slot:has-slotted` rule (display: block) needs to see text.
#   - nested slots: a re-slotted, empty `<slot slot=lead>` matches (light=1 with flattened=0). The polyfill's
#     `assignedNodes()` count agrees with it (assigned=1); Firefox's native `:has-slotted` doesn't (slotLead=0).
#   - the slot-level rules (`slot:has-slotted`, `.label :has-slotted`, `.counter :has-slotted`,
#     `.prefix:has-slotted`) style the slot, not the host, so each would need rewriting as `:host(…) slot.x`.
# And CSSWG's csswg-drafts#11859 ("Should :host(:has()) match?", open, last comment 2026-03-28): Selectors 4 says
# `:has()` is invalid inside `:host()`, which takes a compound selector. The group discussed it on 2025-04-03 without
# a resolution; Gecko's maintainer named invalidation as the obstacle, which is what Firefox shows above. Relying on
# it means relying on a selector the specification currently rules invalid.
#
# `CSS.supports()` also can't replace the detection: Firefox reports `:host:has()` as supported and doesn't match it.
