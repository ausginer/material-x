## Scope

**Covered.**

- **The traits plugin** (`packages/vite-traits-plugin/src/plugin.ts`). `emit` now takes `native: boolean` and returns `{ code: magic }` when it is true. Otherwise it returns `magic.toString()` and a map from `generateMap({ source: id, includeContent: true, hires: true })`, which is the dev server's old branch, unchanged. `native(meta)` is `kind !== 'serve' && meta.rolldownVersion === VERSION`, with `VERSION` imported from `rolldown`. Both transforms, `trait-attributes` and `trait-flattener`, call it once per module that they change. The `load` stage already returned a string and a map, and it is unchanged. - **The private plugin** (`packages/vite-custom-element-assets/src/index.ts`). `constructCSSTokens`'s production `transform` makes the same comparison and returns a string and a map whose source is `normalizePath(id)`. It now takes `id` for that. This was its only hook that returned a magic string.
- **Is the version comparison the right discriminator?** It is the check the plan names: _"The test can be `this.meta.rolldownVersion !== VERSION`"_. I read how a host decides. rolldown 1.3.2's transform bridge (`dist/shared/bindingify-input-options-*.mjs`) accepts a magic string only if `ret.code instanceof RolldownMagicString`. That class is the `BindingMagicString` of the native binding the host loaded, which each `rolldown` copy resolves as `@rolldown/binding-<platform>` by ordinary node resolution. When the versions differ, the bindings differ, and the string-and-map path is correct for any host. So a different version is never a false "native". The comparison can only be wrong for two copies of one version. See `reviewer-1`.
- **Is `kind !== 'serve'` correct?** `kind` is set in `configResolved`: `'serve'` for `command === 'serve'`, otherwise `'library'` or `'application'` from `build.lib`. It stays `'library'` in a tsdown or rolldown host, which calls no `configResolved`. With the guard, the dev server gets a string and a map whatever its `rolldownVersion` is, which is its behavior before task 3. The guard is load-bearing and tested. When I removed it, leaving `meta.rolldownVersion === VERSION`, the existing dev-server test _"should flatten a component of a layer (b) trait from source on the dev server"_ (`tests/vite.node.test.ts:207`) failed.

## Findings

### reviewer-1

**Question for the architect. Tier C as established, and Tier A if a package manager can produce the tree. A host and a plugin on two copies of one `rolldown` version, each with its own native binding, still drop the plugin's edit with exit 0. The check the plan prescribes can't see that case, and the plan's property covers it.**

- **The plan's property:** _"whenever the host's `rolldown` isn't the plugin's copy"_, the plugins return a string and a map. **The mechanism it allows:** _"The test can be `this.meta.rolldownVersion !== VERSION`"_. The implementation uses that mechanism exactly. So this isn't a defect against the plan. It is a gap between the plan's property and its mechanism, and that is the architect's call.
- **The implementer's limit is narrower than recorded.** RF-55's bullet and the PR body say that two copies of one version, _"installed at two paths, would still drop the edit"_. Two JavaScript copies of `rolldown` aren't enough. The host's `instanceof` compares the class of the native binding, and each copy resolves `@rolldown/binding-<platform>` by node resolution. The edit is dropped only when the two copies also load two copies of the binding.
- **Evidence** ([script](checks/same-version-copies.sh), [reading](checks/same-version-copies.txt)). The tree was copied from the workspace's rolldown 1.3.2, with no package manager. A stand-in plugin makes the plugins' exact check and returns the magic string when the versions are equal.
  - **`shared-binding`:** a nested `rolldown` 1.3.2 with no binding beside it resolves the host's `.node` file. The versions are equal and the edit is kept.
  - **`own-binding`:** a nested `rolldown` 1.3.2 with its own binding copy. The versions are equal, the bindings differ, and the output still reads `MARK`: the edit is dropped, and the build doesn't fail.
- **Reachability isn't established.** No probe in this unit or in the plan had a package manager produce two binding copies of one version. In an isolated layout, one version is one store entry, and `rolldown` 1.3.2 declares no `peerDependencies` that would split it into variants. In a hoisted layout, a nested duplicate would need its own nested binding while the root's binding has the same version. I didn't construct that with aube.
- **Why it matters.** Under `CONTRIBUTING.md` §1.1's gate (a), the tree is the package manager's output and not the integrator's misuse. If it can occur, a correctly integrated consumer ships unflattened compositions, which is Tier A. The record and the PR describe the limit more broadly than the probe shows.
- **Required property, for the architect to decide:** either the plan's property is restated to what the version check delivers (the host's `rolldown` _version_ differs), with the narrowed limit recorded; or the check discriminates the host's binding instance, so that the property holds as written. Either way, RF-55 and the PR state the limit as the probe shows it.
